# 수집기 프로세스 재사용 비교 — 2026-09-23

## 비교 전 고정

- 원인 가설: 운영 worker가 URL마다 Chromium 기반 Edge를 시작·종료하므로 불필요한 프로세스 비용이 발생한다. 전체 지연에서 지배적인지는 아직 미측정이다.
- 기준선: 변경 전 collect.cjs/worker.cjs를 `.runtime/collector-reuse-baseline/`에 보존한다. 시간 계측만 추가한 페이지별 프로세스 방식과 작업별 프로세스 재사용을 비교한다.
- 유일한 실행 변경: 브라우저 프로세스 수명. 페이지별 독립 context, 순차 실행, 동일 브라우저/viewport/locale, GET·출처 제한, DOM 수집, 대기, FIFO, 판정 입력과 프롬프트는 유지한다. 새 라이브러리·HTTP 우회·리소스 차단·병렬화는 추가하지 않는다.
- 시간: launch, context 준비, 페이지 생성, navigation, readiness, extraction, page/context/browser 종료와 종단 wall time을 분리한다. 실패·취소도 기록한다. 시간 진단은 판정 근거나 snapshot hash에 넣지 않는다. 기존 collection_elapsed_sec는 과거 호환용으로 유지하고 최적화 평가는 시작·종료를 포함한 wall time을 쓴다.
- 자료: 기존 scope-site 2개 전체(27/28 페이지), 새 동작 진단 fixture(인라인 분할/장문/조상 스타일/댓글 지연/중첩 iframe/저장소 격리/차단 자원/클릭·늦은 타이머의 알려진 한계). 모두 로컬에서만 제공한다.
- 같은 URL 순서로 3쌍 반복, baseline→reuse / reuse→baseline / baseline→reuse. 각 방식은 동일한 새 context를 사용한다. 기존 정답은 수집/탐색에 전달하지 않고 수집 후 채점에만 사용한다.
- 채택: 모든 비교의 원문·정규화·위치·스타일·좌표·문맥·링크·기법 관찰 동일, 기존 정답 수집 손실 0, 동적/격리/오류/취소/재개 검사 통과. 각 자료군에서 3쌍 중 2쌍 이상 빨라지고 총 wall time 중앙값 5% 이상 감소해야 한다. 미통과하면 운영 기준선을 유지한다. 결과 후 기준 완화·대기 튜닝은 하지 않는다.
- LLM 호출 0. 수집 재현율과 근거 일치는 광고 의도 F1/정밀도 개선의 증거가 아니다. 기존 자료는 회귀이며 새 fixture도 동일 제작자의 합성 진단으로 실사이트 일반화 홀드아웃이 아니다. 기존 누락·차단 경계의 한계를 별도로 보고한다.
