# Phase 1 지연 개선 세 후보 비교

실제 HCX 96회와 저장 자료 재생을 통한 독립 진단. 운영 승격과 진단 통과를 구분한다.

## 범위

운영 소스는 변경하지 않았다. 최대12개 묶음, HCX-007 none, 출력512, 58k TPM을 유지했다. 새 학습·Phase2 평가 없이 기존 Phase1의 실제 요청을 사용한 회귀 진단이다. 조건별 원인 해석을 위해 세 변경을 한꺼번에 합치지 않았다. 분석은 병렬로, 유료 API 조건은 서로 할당량을 빼앗지 않도록 분리했다.

실제 요청 실험은 전체 516개에서 정답을 보지 않고 균등 선택한 24개, 238후보를 사용했다. 정답 위치와 대응되는 고유95개(광고50·정상45)가 정확도 평가 대상이다. 분할 후보 및 정답 위치 중복은 없다. 미라벨143개는 판정 일관성만 확인하며 정상으로 간주하지 않는다. 전체 사이트 F1이나 미사용 독립 평가가 아니다.

## 1. 동일 요청의 동시 실행

순차/동시2/동시2/순차로 반복하고 조건 사이61초를 비웠다. 요청 본문·ID·배치 구성·순서는 동일하다. 공유 예약량58k와 발송1초 간격을 유지한다. 요청별 원문·UUID·상태·원응답을 별도 파일로 보존하며 불완전 응답은 격리하고 자동 재요청하지 않는다.

현재 운영의 단일 inflight 기록과 `calls.at(-1)`을 통한 격리 요청번호 귀속은 병렬 실행에 적합하지 않다. 실제 createSession의 역순 부분응답 주입에서 요청1의 격리번호가2로 붙는 것을 재현했다. 연구용 요청별 기록으로 우회한 실측은 운영 중단·재개의 안전성 검증을 대체하지 않는다.

| 조건 | 실제 처리시간 | TP / FP / FN | 의미 F1 | 격리 묶음 |
|---|---:|---:|---:|---:|
| 순차 A1 | 101.630초 | 44 / 13 / 6 | 82.24% | 1 |
| 동시2 B1 | 81.543초 | 44 / 13 / 6 | 82.24% | 1 |
| 동시2 B2 | 81.632초 | 44 / 13 / 6 | 82.24% | 1 |
| 순차 A2 | 102.022초 | 44 / 13 / 6 | 82.24% | 1 |

평균101.826→81.5875초로19.876% 감소했다. 정밀도77.19%, 재현율88.00%는 네조건 모두 같고 정답 위치에서 기존 정탐 손실·새 오탐은0이다. 매조건 같은12후보 묶음이 격리되어226후보만 확정됐다. 격리를 정상 처리하거나 평가에서 광고 FN을 제거하지 않았다. B1에서 미라벨 footer 1개의 게시행위가 이용권유→일반정보로 달라져 광고 이진판정도 변했다. 정답이 없어 F1에 포함하지 않았으며, 전체238후보의 판단이 모두 같았다고 해석하면 안 된다. 같은 모델·본문에서도 판정 변동은 남고 병렬 실행이 원인이라고 단정하지 않는다.

실제96회/288,042토큰, 미확인0, 유효/격리 외 응답오류0이다. 4개의 인접 요청 응답 역전이 실제 발생했고 원응답·후보·요청별 UUID 귀속 감사가 통과했다. 원래18개 운영 소스의 해시 및 Phase2 manifest/평가0 상태도 유지됐다. 실험 전체549.868초에는 조건 사이61초 냉각3회가 포함되며, 표의 처리시간에는 포함하지 않는다.

FN6 중5개는 모든 조건에서 같은 묶음이 격리된 미판정 광고이고 나머지1개는 의미 판정 누락이다. 이번 동시화는 이 불완전 응답 문제를 해결하지 않았다.

동시 요청에서 공유 토큰 예약 대기가 늘어 API서비스 합계 자체는 거의 줄지 않았다. 따라서 2배 처리나 대형사이트25분 완주를 보장하지 않는다. 원래516요청 시간 모사에서는 약32분으로 투영됐으나, 이 역시 실제 종단 측정이 아니다.

**판정: 1번은 후속 운영 통합의 우선 후보로 유지한다.** 소규모 정확도·지연 진단은 통과했지만 운영의 단일 inflight를 그대로 쓰는 변경은 채택하지 않는다. 요청별 중간 저장과 중단·재개를 구현·검증한 뒤 동일25분 종단 비교가 필요하다.

## 2. CPU 기법 판정·저장과 API 대기 중첩

전체516묶음을 저장 응답으로 재생하고 실제 운영 AntiSpoof를 CPU에서 실행했다. 정상 처리된4995판정은 기법 라벨·확률·근거가 일치했다. 원래25분 마감에서 발생한1 timeout·2 unavailable은 시간 제한 없는 재생에서 근거가 생성됐다. 이3개는 코드가 이미 자모/투명/자모를 관찰했으므로 새기법 정탐3개 또는 F1 향상이라고 보고하지 않는다.

원래 마감 실패3개의 기록을 보존한 저장 재생에서4998커밋과151페이지 출력이 일치했다. 이는 복구된 CPU결과까지 모두 같다는 뜻이 아니다. 전체 재생388.34초 중 AntiSpoof180.16초였다. 과거 API서비스2208.57초와 이상적으로 중첩한 모델에서 약180.01초 절감 여지가 있으나 실제 운영 속도 개선값은 아니다.

저장 읽기21.35만회에141.06초가 측정됐다. 저장·발행 계측값에는 중첩되는 함수가 있어 각 시간을 단순 합산하면 안 된다. 반복 결과 재발행은 별도 병목으로 남기며 이번 실험에서 알고리즘을 함께 바꾸지 않았다.

추가로 전체에서 균등 선택한16묶음/163후보에 원래 API응답 시간만큼 대기하는 모사 요청과 실제 CPU를 연결했다. 순차73.363→중첩69.618초로5.10% 단축됐고163판정과 커밋 순서는 같았다. 양 조건은 같은 모델 워밍업 이후 실행했으며 공통로드6.51초는 제외했다. 원응답 영구 저장→CPU대기→커밋 상태 분기와 미확인 전송 재개 거부 검사를 통과했다. 실제 프로세스 강제 종료·브라우저·제공사 TPM·25분 운영 실험은 아니다. 반복 실행 및 실제 운영에서 같은 절감을 보장하지 않는다.

**판정: 2번은 보조 후보로 보존하며 단독 운영 승격은 보류한다.** 1번 통합 과정에서 응답 저장과 CPU대기 상태를 분리한 뒤 추가 이득을 검증하는 편이 합리적이다. 1번19.9%와 2번5.1%를 합산한 성능을 주장하지 않는다.

## 3. 반복 문맥의 무손실 공유표

전체516요청/5070후보의 역복원 일치를 확인했다. 실제 변환 가능한 요청은222개이며 전체 JSON문자3.53%, 로컬 예약 토큰 추정0.96% 감소다. 입력을 코드로 복원할 수 있다는 사실이 HCX의 동일 의미 해석을 보장하지는 않는다.

추가 참조 해석 위험에 비해 큰 지연 개선을 기대할 근거가 약해 유료 확대와 운영 채택을 하지 않는다. 0.96%는 속도 개선의 수학적 상한이 아니며 실제 토큰·의미F1·속도는 미측정이다.

## 최종 채택 검토

1번을 다음 운영 통합 후보로 선택하고, 2번은 보조 후보, 3번은 이번 비교에서 미채택으로 종료한다. 이번 소규모 비교만으로 운영을 교체하지 않는다. 특히 현재 단일 inflight 구조를 유지한 Promise.all 적용은 안전 관문에서 탈락한다. 25분 비교는 해당 실행 구조가 검증되지 않아 이번에는 실행하지 않았다.

후속 순서는 요청별 영구 상태·역순 응답 귀속·중단 후 원응답 재사용 검증 → 1번 단독의 동일25분 종단 비교 → 유의미할 때만 2번 추가다. 이미 입증된 판정 모델·기법 모델·FIFO 탐색·입력 문맥은 그대로 유지한다. 저장 반복 읽기 개선은 별도 요인으로 비교해야 한다.

주요 한계는 소표본95정답 위치, 기존 관찰자료, 같은 합성 생성자의 반복 문맥, 미라벨1개의 판정변동이다. 이번 결과는 새로운 일반화 성능 개선이나 오류 해결의 증거가 아니라 동일 입력의 처리량 개선 가능성이다. Phase2는 미사용으로 보존했다.
