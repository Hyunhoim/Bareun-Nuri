# 점진 실행·혼합 사이트 실제 비교 결과

2026-09-23. **점진 실행은 별도 CLI에서 구현·검증했고, 탐색 정책 교체는 미채택이다.** FIFO를 비교 기준으로 유지한다. 우선순위 탐색은 자료에 따라 득실이 달랐고, 게시판 필터는 관리자 공지와 그 댓글의 광고를 제외했다. 기존 2·3단계의 의도·기법 오류는 해결됐다고 간주하지 않는다.

## 구현과 검증 범위

`agent/experiments/progressive.cjs`는 한 페이지 수집 → 전역 후보 16개 배치 판정 → checkpoint/부분 결과 저장 → 다음 수집을 반복한다. 페이지마다 짧은 배치를 마감하지 않아 동일한 수집 순서에서는 기존 요청 구성이 유지된다. 마지막 잔여 배치는 전체 탐색 종료 때 처리한다. 예산 중단 때 남은 후보는 미판정으로 보존한다.

- `checkpoint.json`: 체크섬을 포함한 원자적 저장. 후보, 판정, 방문/대기/제외 URL, 제외 이유, 누적 호출·활성 시간, 요청 중 상태를 보존한다.
- `run.json`: 완료/부분 완료/실패와 중단 이유·범위. `result.partial.json`은 진행 결과, 전체 탐색·판정이 끝난 경우에만 `result.json`을 만든다. 필터로 제외한 페이지가 남으면 완료가 아니다.
- 같은 실행 디렉터리에서 누적 페이지·호출·시간 한도를 늘려 재개한다. 소스·데이터 manifest와 모델·전략·시작 URL이 달라지면 거부한다. 이미 저장된 판정은 다시 호출하지 않는다.
- 응답/저장 여부가 불명확한 요청은 자동 재시도하지 않는다. 외부 API의 정확히 한 번 실행을 보장하는 기능은 아니다. 해당 요청은 기록을 확인해야 한다.
- 단일 로컬 프로세스 잠금과 죽은 소유자 복구를 사용한다. 잠금 회수 경쟁은 별도 짧은 gate로 막는다. gate 안에서 비정상 종료되면 수동 확인이 필요하다. 여러 컴퓨터의 분산 실행은 지원하지 않는다.
- 활성 시간은 체크포인트 기반이다. 강제 종료 직전 저장되지 않은 시간 구간의 정확한 복원이나 네트워크 요청의 원격 취소까지 보장하지 않는다.

검사 통과: 기존/점진 요청 body 및 16개 배치 일치, 동일 입력의 결정적 응답·최종 findings 일치, 페이지·호출·시간 중단, 코드 변경/체크섬 변조 거부, 결과 보존, 미확정 요청 재시도 거부. 실제 자식 프로세스를 종료한 뒤 재개해 저장된 16개를 보존하고 나머지 6개만 처리했다(22개/총 2호출, 모의 판정).

실제 브라우저에서 기존 수집기와 점진 수집기의 짧은 후보 원문·위치가 동일함을 확인했다. `npm.cmd test --prefix agent` 전체 통과. 첫 실행에서는 취소된 탐색의 `net::ERR_ABORTED`가 기존 테스트의 허용 문구와 달라 실패했다. 실제 abort 상태·이유를 함께 확인하도록 테스트만 보강한 뒤 전체 재검사했다.

**운영 웹 worker는 이번 실험 경로를 사용하지 않는다.** 작업 시작 시점 대비 worker/LLM 프롬프트·계약/output 코드가 동일하다. 수집기에 추가한 navigation/긴 문서/한 페이지 옵션은 기본값에서 비활성이다. 웹 UI에서 중단·재개하는 기능까지 구현한 것은 아니다.

## 자료와 고정 조건

`test-set-v3`: 개발 40페이지 + 최종 확인 40페이지, 각각 광고 20개·정상 40개 정답. 제목·본문·댓글, 정상 게시판, 이용자 게시판, 일반 안내/관리자 공지의 광고, 공지의 이용자 댓글, 깊은 메뉴·불투명 링크·페이지 이동, 긴 본문·인라인 분할을 포함했다. private 정답은 HTTP나 LLM에 전달하지 않는다.

각 조건은 최대 **20페이지 / API 시도 12회 / 활성 시간 600초**, HCX-007, temperature 0, thinking none, seed 42, 출력 3072, 순차 배치 16으로 고정했다. FIFO → 우선순위 → 필터 순으로 개발/확인에서 각각 한 번 실행했다. 조건 사이의 점수·프롬프트·자료 수정은 없었다.

우선순위는 기존 링크 점수 + 매 네 번째 FIFO 선택이다. 필터는 이 순서에 더해, 명시적인 관리자 전용 안내가 있는 목록의 내용 링크를 제외한다. 참여 기능이 있으면 이용자 영역, 불명확하면 유지한다. **모든 비게시판 페이지를 제거하는 극단적인 필터보다 보수적인 정책**인데도 누락이 발생했다.

모의 전체 탐색은 두 사이트 모두 40페이지/원래 후보 326개/분할 후보 330개를 완료했고, 60개 정답 위치와 원문이 각각 정확히 대응했다. 모의 판정 수치는 정확도로 사용하지 않았다.

## 실제 HCX 결과

의미 판정: 전체 사이트의 광고 20개를 분모로 사용한다. 미방문·미판정·검토 광고도 FN이다. 아래 정밀도 100%는 4개 양성에서 오탐이 없었다는 뜻이며 전체 사이트 탐지 완료를 뜻하지 않는다. 라벨 밖 확정 양성은 여섯 조건 모두 0개였다.

| 자료 | 전략 | TP / FP / FN | 정밀도 | 재현율 | 의미 F1 | 요소×기법 F1 | 호출 | 토큰 | 시간(초) |
|---|---|---|---:|---:|---:|---:|---:|---:|---:|
| 개발 | FIFO | 5 / 1 / 15 | 83.33% | 25% | 38.46% | 38.46% | 10 | 79,390 | 261.7 |
| 개발 | 우선순위 | 5 / 8 / 15 | 38.46% | 25% | 30.30% | 30.30% | 11 | 85,679 | 263.4 |
| 개발 | 필터 | 2 / 4 / 18 | 33.33% | 10% | 15.38% | 15.38% | 10 | 78,850 | 245.7 |
| 확인 | FIFO | 2 / 3 / 18 | 40% | 10% | 16.00% | 8.00% | 10 | 78,760 | 245.9 |
| 확인 | 우선순위 | 4 / 0 / 16 | 100% | 20% | 33.33% | 33.33% | 11 | 72,049 | 223.7 |
| 확인 | 필터 | 4 / 0 / 16 | 100% | 20% | 33.33% | 33.33% | 11 | 72,047 | 231.8 |

모두 20페이지 예산에 도달해 **부분 완료**로 종료했다. 실패 종료는 없다. 실제 63회, **466,775토큰**, 활성 시간 합계 약 24분 32초. 전부 HTTP 200, 재시도·형식 복구 요청 0회. 토큰은 응답 usage 실측이며 원화 청구 금액을 추정하지 않았다. 예산은 최대치가 같으며 실제 사용량은 페이지별 후보·문서 길이에 따라 달랐다.

## 병목을 분리한 해석

| 자료/전략 | 도달한 광고 | 판정한 광고 | 미방문 FN | 방문 후 미판정 FN | 검토 FN | 정상 판정 FN |
|---|---:|---:|---:|---:|---:|---:|
| 개발 FIFO | 6 | 6 | 14 | 0 | 0 | 1 |
| 개발 우선순위 | 6 | 6 | 14 | 0 | 1 | 0 |
| 개발 필터 | 3 | 3 | 17 | 0 | 1 | 0 |
| 확인 FIFO | 3 | 2 | 17 | 1 | 0 | 0 |
| 확인 우선순위 | 4 | 4 | 16 | 0 | 0 | 0 |
| 확인 필터 | 4 | 4 | 16 | 0 | 0 | 0 |

1. **주요 누락은 탐색 범위다.** 이 표본에서는 전체 광고의 70~85%가 미방문 상태였다. 모든 전략에서 깊은 게시판 광고 4개/분할에 도달하지 못했다. 대기 URL 수는 이미 발견한 URL만 세므로 전체 미방문 페이지 수와 같지 않다. 과거 판정 완료 패널의 F1과 이 제한 예산 전체 사이트 F1을 직접 비교하면 안 된다.
2. **게시판 필터는 관리자 공지의 안전성을 추정할 수 없다.** 개발에서 FIFO가 찾은 관리자 본문 2개와 공지 댓글 1개가 제외됐다. 필터는 분할마다 관리자 상세 4페이지를 제외했다. 확인용에서는 우선순위도 예산 내 이 영역에 도달하지 못해 두 정책의 점수가 같았다. 이것은 필터가 안전하다는 증거가 아니다.
3. **순서를 바꾸면 판정도 달라졌다.** 개발 FIFO/우선순위의 공통 판정 정답 26개 중, 동일 후보 JSON인 정상 7개가 양성으로 바뀌었다. 예방 인용의 오탐이 주된 문제다. 후보 자체가 같아도 함께 들어간 배치와 실행 시점은 달랐다. 배치 문맥 영향과 모델 자체 변동을 이 단회 비교로 분리할 수 없다. 탐색 규칙만의 효과라고 단정하지 않는다.
4. **긴 본문은 수집 성공과 의미 판정 성공이 다르다.** 개발의 긴 안내 광고는 원문 구간을 모두 판정했지만 FIFO는 정상, 다른 둘은 검토로 남겼다. 확인 FIFO의 긴 광고는 의미 양성이지만 요소×기법 판정에서 오류가 있었다. 분할·복원만으로 장문 문제를 해결했다고 볼 수 없다.
5. **지연은 API 응답과 입력량 대기가 크다.** 조건별 API 서비스 시간 합계는 약 163~182초, 입력량 제한 대기는 긴 본문을 방문한 네 조건에서 약 40~43초였다. 나머지는 수집·브라우저 시작/종료·저장 등이다. 비교 공통으로 페이지마다 브라우저를 새로 띄우는 최소 구현이므로 운영 처리량의 상한으로 해석하지 않는다. 병렬 호출은 추가하지 않았다.

개발에서 순서 변경으로 늘어난 오탐과 필터의 기존 양성 손실을 실행 중 즉시 보고했다. 이 자료를 보며 규칙/프롬프트를 재조정하지 않았다.

## 입력 예산 후속 안전 보완

별도 사전 계획 `progressive-input-budget-plan.md`에 따라 여섯 조건 종료 후 적용했다. 긴 원문은 12,000자를 넘을 때만 최대 6,000자/400자 중첩 구간으로 나누고 원문 offset·위치를 보존한다. 요청 조립은 기존 createSession을 그대로 사용하여 **HTTP 전송 전에** 추정하고, 52,000 추정 토큰을 초과할 때만 순서대로 배치를 줄인다. 하나의 후보조차 초과하면 자르거나 정상 처리하지 않고 명시적으로 실패한다.

실험 당시 소스 99개는 `.runtime/progressive-live/frozen-source/`에 manifest 해시 검증 후 보관했다. 실제 사용한 **63개 요청 전부 새 처리에서도 같은 ID·배치·요청 토큰 추정치를 유지**했다(최대 추정 51,348). 저장된 부산 자료의 27,816자 원문은 5구간이며, 최종 검증에서 전체 요청 추정 84,657 → 2구간 37,139 + 3구간 51,619로 나뉘었다. 앞선 간이 검사 84,630과의 차이는 요청 메타데이터 구성 차이다. 내용 누락·중복 판정 없이 순서를 보존했고 외부 호출은 0회였다.

이는 자원 한도 검사다. 실제 부산 원문을 HCX에 전송하지 않았고, 새 장문 배치 구성의 의미 정확도를 검증한 것은 아니다. 실제 정확도 표는 보관한 실험 버전의 결과다.

## 채택 판단과 미검증 범위

사전 기준은 두 분할 모두 양성 보존/오탐 비증가와 비용·시간 10% 개선, 또는 동일 예산의 재현율 +5%p/정밀도 비감소였다. 개발에서 우선순위는 재현율 개선 없이 오탐이 늘었고, 필터는 양성 손실과 정밀도 저하가 있었다. **두 정책 모두 미채택**이다. 확인용 개선만 골라 성공으로 판단하지 않는다. 우선순위 역시 확인 FIFO의 일반 안내 양성 2개를 방문하지 않고 이용자 게시판 양성 4개를 대신 찾은 범위 교환이었다.

FIFO가 보편적으로 최선이라고 입증한 것은 아니다. 현 단계에서는 검증된 기준을 유지하고, 점진 실행·부분 상태를 이용해 검사 범위를 명시하는 것이 타당하다. 다음 별도 검증 후보는 영역별 탐색 기회 배분이다. 동일 문구에 맞춘 가중치 조정이나 추가 판정 단계를 이번에 적용하지 않았다.

**과적합 우려:** 개발/확인 모두 같은 제작자의 합성 자료다. 단어·마크업·초기 링크 순서는 다르지만 페이지 연결 구조와 생성 규칙을 공유하고 표현의 다양성도 제한적이다. 관리자 권한을 직접 적은 안내는 실제 사이트보다 분류하기 쉽다. 닮은꼴 표기는 전각 접두 예시로 제한돼 광범위한 문자 위장 검증이 아니다. 긴 정상 인용 문서에 대한 실제 LLM 안전 검증도 부족하다. 이번 결과를 실사이트 일반화 개선으로 확정하지 않는다. 이제 두 분할은 모두 관찰한 진단 자료다.

## 실행과 결과 위치

루트에서 실행한다. 별도 신규 디렉터리를 사용하고 기존 결과는 덮어쓰지 않는다. Node/Playwright 설치 환경은 기존 Agent와 동일하다. 서버는 기본 Codex Python 경로를 사용하며 다른 환경은 `PYTHON_EXE`를 설정한다. 8787 포트가 비어 있어야 한다.

```powershell
node test-set-v3/build.cjs
npm.cmd test --prefix agent
# 무과금 전체 탐색/계약 검사
node agent/experiments/progressive-trial.cjs dry .runtime/progressive-dry-new
# 실제 HCX 호출(6조건, 비용 발생); 키는 agent/.env
node agent/experiments/progressive-trial.cjs live .runtime/progressive-live-new
node agent/experiments/progressive-score.cjs .runtime/progressive-live-new/dev-fifo test-set-v3/private/labels.json dev
```

개별 재개는 **해당 실행의 동일 소스/manifest**와 로컬 사이트 서버가 유지된 상태에서 한다. 한도는 추가분이 아니라 누적 총량이다. live trial 실행기는 자동 서버 종료하므로 재개 전에 같은 사이트를 8787에 다시 띄워야 한다. 보관된 이번 실험 결과는 현재 소스가 변경됐으므로 직접 재개가 거부되는 것이 정상이다.

```powershell
node agent/experiments/progressive-run.cjs http://127.0.0.1:8787/dev/ .runtime/progressive-live-new/dev-fifo fifo 40 24 1200 hcx
```

새 trial도 공유 상한은 96회/900,000토큰이다. 재개 역시 이 상한을 적용한다. 채점 `score.json`은 최초 한 번만 생성한다. 추가 재개 평가는 기존 점수를 먼저 별도 보관해야 한다. 시간/호출 한도를 대회 규정이라고 해석하지 않는다. 대회 문서의 30분 기준은 별도로 준수해야 한다.

증거: `.runtime/progressive-live/comparison.json`, 각 실행의 `score.json`, `checkpoint.json`, `trace.jsonl`, `budget.json`, `manifest.json`, `input-budget-verification.json`. mock 전체 위치 검증은 `.runtime/progressive-dry/verification.json`이다. 커밋·push는 하지 않았다.
