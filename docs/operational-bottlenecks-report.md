# 최신 운영 Pipeline 병목 점검 — 2026-09-25

운영 정책은 FIFO로 고정한다. 이번 작업은 코드/저장 근거/이전 보고서 대조이며 운영 코드 변경과 새 HCX 호출은 없다. 현재 전체 사이트 F1이나 25분 처리량을 새로 측정한 보고서가 아니다. Graphify의 운영 파일 7개를 원본과 대조하고 달라진 llm.cjs 사본을 갱신해 그래프를 재생성했다. 아래 코드상의 현상과 과거 실측, 미검증 가설을 구분한다.

## 현재 실제 경로

React → Spring Boot Jobs → worker → scan: FIFO 선택 → 작업당 재사용 브라우저/URL별 context로 collect → 후보 분할 → 최대 16개씩 순차 HCX 판정 → checkpoint/result/coverage 저장 → 다음 URL.

- 브라우저 재사용은 채택돼 있다. HCX-007 none, 운영의 최대 배치 16, 요청 출력 3,072토큰, 로컬 TPM 예산 52,000, 요청 타임아웃 180초다. 52,000은 현재 코드 설정이며 제공자의 최신 계정 한도를 조회한 값이 아니다.
- 웹 기본 요청은 mock, 40페이지/후보 1,000개/220호출/3,600초다. 실제 HCX 사용 시 provider를 바꿔야 한다. UI/backend/worker가 허용하는 상한은 200페이지/10,000후보/300호출/3,600초이며 페이지별 collector에도 10,000후보 제한이 있다.
- 합의한 25분 구간, 누적 후보 제한 해제, 웹 이어서 검사는 아직 요구사항이다. core 체크포인트 재개 구현과 웹 재개 기능은 다르다.

## 0. 실행 신뢰성과 예산

`worker.cjs:24`의 입력 상한과 `frontend/src/App.tsx:8`의 기본값은 새 계약을 구현하지 않는다. `Api.java`에는 시작/취소 API만 있고 재개 API가 없다. `Jobs.java:103`의 watchdog은 요청 시간+15초이며 새 5분 정리 구간이 아니다.

`scan.cjs`는 전역 후보 상한을 넘는 페이지의 snapshot을 state에 수용하기 전에 중단한다. 같은 한도로 재개하면 해당 페이지 수집이 반복될 수 있다. 페이지별 collector의 후보 10,000개 초과나 원문 단위 100,000자 초과는 예외를 던지고, scan은 그 URL을 시도/방문 실패로 기록한다. 이때 그 호출의 부분 후보는 반환되지 않는다. 이 예외 경로가 최근 FIFO 실사이트에서 실제 발생했다는 뜻은 아니다.

`scan`은 inflight 상태의 재개를 거부하지만 `worker`는 retryTransientTransport=true를 설정하고 `llm.cjs:140`은 fetch failed 시 60초 후 한 번 다시 호출한다. fetch failed만으로 서버 미수신을 증명할 수 없으므로 현재 미확인 요청 자동 재호출 금지 계약과 충돌한다. 외부 네트워크를 차단한 Mock fetch에서 재시도 분기 선택을 재현하고 실제 두 번째 요청 전 취소했다. 재개 보호가 곧 실행 중 재호출 금지라는 이전 설명은 이 코드에 대해 충분하지 않다.

scan의 inflight는 실제 HTTP 전송 전(로컬 토큰 대기 전)에 기록된다. 따라서 단순 대기 중 중단도 요청 확인이 필요한 상태로 남을 수 있다. 예약/전송/응답/확정 저장 상태를 구분할 필요가 있다. worker의 elapsedSec는 scan이 반환한 시간을 우선 사용해 뒤이은 browser close 등을 포함하지 않을 수 있고, result의 finished_at도 최종 프로세스 종료 시각과 다르다. 제출 30분 준수는 전체 경로의 벽시계로 따로 검증해야 한다.

## 1. 수집 → 판정 근거 전달

collector는 raw_text, normalized_text, context, context_evidence, ancestors, nearby, links 등을 저장한다. 그러나 `llm.cjs:82 initialEvidence`는 raw/normalized text, page_title, own_style, signals, nearby, links, frame_depth만 전달한다. 구조화된 소유/인용 문맥과 조상 스타일은 전달되지 않는다. 운영 요청에는 도구 정의도 없으며 응답의 tool_calls는 거부한다. 따라서 모델이 빠진 근거를 도구로 다시 조회한다고 설명할 수 없다.

현재 요청 조립기에 실제 저장 후보를 넣고 전송 직전에 중단하는 검사에서 context_evidence/ancestors 미전달을 확인했다(네트워크 0회). 입력 누락은 확인됐지만 각각이 현재 오답 몇 건을 유발했는지는 새 대조 평가가 필요하다. 전부 무조건 넣으면 주변 광고 근거 혼동과 토큰 증가가 생길 수 있다. 과거 contextual/attributed/direct 경로도 오탐·불확실성 관문을 실패했으므로 입력 필드 추가만으로 개선을 확정하지 않는다.

긴 원문은 12,000자를 넘으면 6,000자/400자 중첩으로 나눈다. 최근 부산 FIFO에서 12,000자 초과 후보 5개는 수집됐다. 원문 구간 보존과 광고 권유/예방 설명의 의미 연결은 별개이며 이 실사이트 장문의 HCX 정확도는 미검증이다.

## 2. 판정 처리량이 탐색 처리량도 제한

`scan.cjs:89`의 drain은 대기 후보가 16개 이상인 동안 계속 순차 판정한다. 완전한 배치를 모두 처리한 후에야 다음 URL을 수집한다. 따라서 후보가 많은 정상 페이지도 다음 광고 페이지 도달을 늦춘다. 이는 FIFO 선택 계산 속도와 다른 병목이다.

최근 실제 FIFO 20페이지의 저장 후보를 다시 집계했다. 아래 호출 수는 모두 16개로 보낸다는 이론적 하한이다. 장문 분할, 입력 상한에 따른 작은 배치, 형식 복구가 있으면 늘어난다.

| 시작점 | 후보 | 최소 호출 | 누적 1,000 초과 페이지 순번 | 누적 10,000 초과 순번 |
|---|---:|---:|---:|---:|
| 부산 게시판 | 3,455 | 216 | 3 | 해당 없음 |
| 대전 게시판 | 6,883 | 431 | 5 | 해당 없음 |
| 부산 메인 | 10,408 | 651 | 2 | 19 |
| 대전 메인 | 14,115 | 883 | 4 | 16 |

순번은 같은 저장 후보를 끝까지 수집한다고 가정한 개수 계산이다. 실제 운영에서는 호출/시간 제한이 먼저 걸릴 수 있다. 최근 실사이트 진단은 누적 후보 제한과 HCX를 적용하지 않았고 페이지별 20,000개 상한을 사용했으므로 현재 운영의 완주 실적이 아니다. 현 최대 300시도·배치16으로는 최대 4,800개의 판정 작업밖에 처리할 수 없고 수집 후보 수와 분할 작업 수는 다르다. 후보 제한 해제 하나만으로 처리량이 해결되지 않는다.

과거 progressive-mixed 실제 호출에서 조건별 API 서비스 합계 163~182초, 긴 입력의 로컬 토큰 대기 약40~43초를 관측했다. 당시 페이지당 브라우저 시작 방식이므로 그 종단 시간을 현재 운영의 정확한 비율로 재사용하지 않는다. worker와 같은 판정 계약의 저장 후보 268개 실험에서는 17회/112,263토큰/274.81초였다. 실제 실사이트 전체에 선형 외삽하지 않는다.

원문만 같은 후보는 과거 86.01%였지만 문맥·스타일까지 같은 후보는 13.15%였다. 재사용안은 호출17→16, 시간7.56% 감소에도 원본 두 회차가 모두 탐지한 광고2개를 잃어 미채택됐다. 메뉴/제목/작성자 일괄 제외, signals 없는 후보 정상 처리, 원문만으로 합치는 방식은 근거가 없다. 병렬화도 로컬 TPM 제한 자체를 없애지 않는다.

## 3. 실제 수집/주소 발견의 공백

- 이전 collector 재사용 진단의 알려진 텍스트22개 중20개 수집. 클릭 후 댓글과 안정화 이후6초 댓글2개는 전후 모두 누락했다. 재사용으로 새로 생긴 오류가 아니다.
- 최근 FIFO는 4시작점 각각20/20접속 성공이다. 140개 정책 합집합의 다운로드/403 실패2건을 FIFO 오류로 인용하지 않는다.
- 저장 기록상 FIFO의 부산 메인 경로3페이지에서 외부 livere embed 스크립트 차단, 민원 페이지1곳에서 about:blank/empty_or_unloaded_frame을 확인했다. 실제 광고/댓글의 누락 수는 확인하지 못했다. 프레임 내부 후보62개가 수집된 사실과 함께 해석한다.
- JS/onclick 링크는 기본 anchor URL 수집만으로 목적지 발견을 보장하지 못한다. 주소 미발견과 페이지 방문 후 추출 누락을 분리한다. 클릭 대상에 대한 읽기 전용 검증 없이 자동 클릭하지 않는다.
- 다른 출처 CSS·JS/비GET 차단은 현재 명시 계약이다. 댓글 생성 또는 스타일 근거를 제한할 수 있으나 모든 차단이 콘텐츠 누락을 의미하지 않는다. 일반 외부 링크 탐색과 필요한 리소스 로딩을 혼동하지 않는다.

## 4. 의미·기법·최종 결과의 계약

현재 기본 HCX는 광고 의도와 관찰 기법을 한 요청에서 함께 출력한다. 코드 관찰기 techniques.cjs의 독립 통합은 미채택 상태다. `output.cjs`는 needs_review 또는 양성이지만 techniques가 빈 결과를 findings에 넣지 않는다. 의미 판정 성공만으로 제출 결과의 검출 성공이 되지 않는다.

worker 계약의 과거 동일 요청 17개 반복에서도 signature5개가 달랐고, 정답76개 원본 반복의 FP는7→3이었다. 예방 인용·근거 귀속·보류 판단과 배치/반복 변동을 미해결 문제로 유지한다. 이 선별 패널의 F1 89.74%/94.59%를 현재 전체 사이트 F1로 인용하지 않는다. 별도 isolated 의미 패널 및 관찰 통합 F1 96.77%도 현재 worker 성적으로 사용하지 않는다.

HCX medium의 부분 비교는 13쌍의 응답에서 형식 실패와 지연 증가를 보였으나 direct 실험 계약이고 미완주였다. 운영 none의 의미 성능 한계나 추론 전체의 무효를 입증하지 않는다. 지금 추론 강도/모델 교체를 우선순위로 올릴 근거는 없다.

## 5. 추출·저장 비용과 탐색의 한계

최근 실사이트 고유140시도의 수집 계측 합계는 extraction385.87초, navigation314.20초, readiness147.70초였다. extraction은 DOM뿐 아니라 스타일·위치·프레임·후보 가공도 포함한다. 합집합 진단이며 FIFO만의 시간이나 HCX 포함 종단 비율이 아니다. 이전 소형 합성 자료의 '재사용 후 대기가 약70%'와 분모/구조가 다르다.

readDocument는 후보별 조상 스타일/좌표, selector 유일성, 여러 DOM 탐색을 수행한다. scan은 배치마다 누적 checkpoint와 결과를 동기 직렬화·저장하며 visited.includes/pending.some 등을 반복한다. FIFO에서도 과거 Bandit용 profile/feedback 계산을 수행한다. 중복 작업 절감 가능성은 있으나 현재 실제 시간·메모리 기여도가 없어 큰 가속을 주장하지 않는다. 동기 작업이 길어지면 타이머 처리도 늦어질 수 있으므로 누적 제한 해제 전에 저장·종료 지연을 확인한다.

최근 복제본 FIFO @20은 광고24위치 중 평균3.73도달/12.63발견 후 대기/7.65주소 미발견이었다. 미방문이 주된 손실이나 저장 범위 밖 경계를 포함한 진단이지 실사이트 전체 광고 정답이 아니다. FIFO는 유지하고 후보/API/주소 발견 병목을 개선한다. URL 구조나 게시판 여부로 영역을 제외해 점수를 올리지 않는다.
