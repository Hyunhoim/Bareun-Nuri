# 동일 요청 동시 2개 처리량 진단

2026-09-26. 운영 변경 없음, 외부 API 호출 0회.

## 가설과 비교 범위

동일한 원문·문맥·후보 4개 배치와 요청 순서를 유지하면, 최대 2개 요청의 응답 대기를 겹쳐 처리량을 높일 수 있다는 가설을 검증했다. `.runtime/scale-large-live-v1`의 실제 성공 요청 467개를 고정했다. 토큰 분당 52,000, 예약 창 61초, 요청 간격 1초, 출력 512, 최대 600호출을 유지한다. 성공 응답 후 예약을 입력 실사용 토큰+512로 정정하는 운영 로직도 재생했다.

실제 공급자 동시 처리 지연은 새로 측정하지 않았다. 이 단계는 후속 실제 비교 가치와 안전성 진단이며 운영 채택 검증이 아니다. 부모 실험 계획의 채택 기준을 변경하지 않는다.

## 시간 재생

| 조건 | 순차 | 동시 2개 | 감소 |
|---|---:|---:|---:|
| 관측된 요청 전 수집·저장 간격 보존 | 1,495.146초 | 1,415.103초 | 80.043초 / 5.35% |
| 요청 전 간격 제거, 모델·quota만 비교 | 1,464.181초 | 1,404.321초 | 59.860초 / 4.09% |

원래 첫 요청 시작부터 마지막 응답까지 실측 1,497.539초이며, 순차 재생은 2.393초 짧았다. 운영의 1초 quota 재검사와 응답 시 예약 정정을 모사하되 실제 이벤트루프·디스크 타이밍 변동까지 재현하지 않았기 때문이다. 수집 간격 포함 비교의 감소분 모두를 순수 API 동시성 인과효과로 해석하지 않는다.

모든 조건은 동일한 관측 467요청을 끝낸 결과다. 남은 약 80초로 새 광고를 몇 개 더 찾을지는 관측하지 않았고, 새로운 F1·25분 도달률을 산출하지 않았다. 원래 이후의 미판정 요청에 관측된 응답시간이나 의미 판정값을 임의로 붙이지 않았다. 재생은 작업 준비 의존성을 단순화하므로 실제 FIFO 수집+SRPT 스케줄러 속도개선을 입증하지 않는다.

## 실제 createSession의 네트워크 stub 검사

`node agent/experiments/throughput-concurrency-stub.cjs`로 다음을 확인했다.

- 순차와 동시 요청의 직렬화 body, 후보 순서와 최종 판정 동일.
- 두 번째 응답을 먼저 반환해도 각 Promise의 후보 ID 귀속 보존.
- 요청번호 중복 없음, lifecycle callback에 각각 올바른 call_number 전달.
- 하나의 createSession 공유 quota가 두 번째 요청을 차단하며 대기 중 취소 시 미전송.
- 전송 결과를 알 수 없는 통신 오류는 자동 재시도하지 않음.

이는 안전한 운영 체크포인트 구현을 대신하지 않는다. `bounded-scan.cjs`는 `state.inflight` 하나에 준비·전송·응답을 기록하고 판정 저장 후 다음 스케줄링으로 넘어간다. 그대로 동시 `decide`를 연결하면 lifecycle이 덮어써질 수 있다. 동시 운영은 요청별 영속 lifecycle, 확정 배치 커밋, 비순차 응답과 부분 실패 및 재개를 별도로 구현·검증해야 한다. 이번에는 운영 코드를 수정하지 않았다.

## 판단

입력·배치 변경 없이 시험할 수 있는 후보이지만, 현 52,000 TPM 조건에서 추정 절감은 약 4~5%로 제한적이다. 더 큰 이득이 검증된 다른 독립 개선안보다 우선시할 근거는 약하다. 실제 짧은 동일입력 비교는 가능하나, 이번 재생만으로 동시 2개 운영을 채택하거나 전체 탐지 성능 향상을 주장하지 않는다.
