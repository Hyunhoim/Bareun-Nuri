# Phase 1 후처리 지연 진단

2026-10-01. 운영 소스 변경·API 호출·학습 없이 기존 Phase 1 저장 근거와 의미 판정을 실제 CPU AntiSpoof 및 운영 저장 경로로 재생했다. **후처리를 다음 API 대기와 겹치는 것은 유망하지만, 이번 수치는 실제 중첩 실행의 속도 개선값이 아니다.**

## 범위와 방법

- 원자료 `.runtime/phase1-full-1790774023853/scan`: 151페이지, 516묶음, 4,998확정 후보, 72격리 후보.
- 동일 FIFO/SRPT8/aging8/12묶음/수집 동시5 선택 로직에 저장된 페이지를 공급했다. 브라우저와 HCX 호출은 하지 않았으며 묶음 순서 516개를 원래 이력과 대조했다.
- 의미 판정은 저장값을 고정하고 AntiSpoof v1.0을 실제 CPU 8스레드로 재실행했다. 모델 프로세스는 한 번 로드했다. 원래 실행은 25분 종료와 재개 사이 두 번 로드하므로 차이를 유지한다.
- `createStore`의 `put/load/commit/quarantine/output/write/read` 호출 시간을 계측했다. 별도의 저장 정책을 구현하지 않고 운영 저장·전체 결과 발행 경로를 실행했다.
- `phase1-speed-postprocess-v1`은 JSON 직렬화에서 사라지는 undefined 속성 비교로 중단됐다. v2는 원래 마감시각의 AntiSpoof 실패 3개가 무시간제한 재생에서 복구되는 차이를 발견해 중단됐다. 두 기록은 보존했다. 유효 완료본은 v3이다.

## 실제 측정

| 항목 | 시간 |
|---|---:|
| 전체 오프라인 재생·검증 | 388.34초 |
| AntiSpoof annotate 합계 | 180.16초 |
| 최초 양성 묶음(모델 로드 포함) | 6.24초 |
| 저장 자료 read 213,480회 | 141.06초 |
| 외부 write 2,369회 | 16.31초 |
| commit 510회 | 3.42초 |
| 페이지 기법 통합·output 516회 | 3.08초 |
| evidence put 151회 | 2.31초 |
| load 516회 | 2.53초 |

메서드 시간은 내부 호출·기타 직렬화의 범위가 다르므로 전체 시간을 재구성하기 위해 단순 합산하지 않는다. read는 전체 결과 재발행과 기존 위치 중복 확인 등에 사용된다. 원래 실시간 실행의 후처리 시간이 아니라 현재 장비에서 API·브라우저 대기를 제외한 재생 시간이다. 과거 전체 46분30초에서 이 시간을 빼서 새 종단 시간을 확정할 수 없다.

현재 이미 AntiSpoof 모델은 후보마다 로드하지 않는다. 세션별 단일 Python 서비스가 재사용되므로 모델 재사용 자체를 새 개선안으로 제시하지 않는다. 기법 통합·개별 commit은 작고, 반복된 저장 자료 읽기와 전체 결과 재발행이 더 크다.

## 정확성 및 마감 오류

- 원래 CPU 실패 3개를 제외한 **4,995개 공통 판정은 라벨·근거가 동일**했다. 비교 가능한 확률의 최대 차이도 0이었다.
- 원래 285번째 요청의 3개 광고는 첫25분 마감 시 `antispoof_timeout` 1개, `antispoof_unavailable` 2개가 남았다. 제한 없는 재생에서는 JAMO/없음/JAMO 보조 근거를 얻었다.
- 해당 지정 광고의 정답은 JAMO/TRANSPARENT/JAMO이며 기존 코드가 이미 같은 기법을 확정했다. 따라서 이것을 신규 광고 회복이나 모델 F1 개선으로 주장하지 않는다. 검토 진단 감소 가능성이며 마감·재개 정책 문제다.
- 저장 경로 검증은 이 3개의 원래 실패 근거를 그대로 보존해 수행했다. 그 조건에서 원래 4,998 커밋 및 151페이지 최종 출력과 완전히 같았다. **새 CPU 결과 전체가 원래와 동일했다는 뜻이 아니다.** 원래/새 근거는 `timing.json`의 `source_failures`에 모두 남겼다.
- 17개 운영 소스 해시 불변, 6묶음 격리·72미판정 유지. Phase 2는 접근하지 않았다.

## 중첩 가능 범위와 판단

원래 API 응답 시간 합은 2,208.57초다. 이 시간을 그대로 사용하고 모든 요청이 미리 준비됐다고 가정한 두 단계 큐 계산에서:

- API + 이번 CPU 순차: 2,388.73초
- API + CPU 이상적 중첩: 2,208.72초
- **CPU만의 중첩 절감 상한: 180.01초(약3분)**

네트워크·수집·공유 TPM 대기·동시 부하·결과 영구 저장을 제외한 계산이다. 실제 네트워크 동시화 성과나 25분 개선 성능이 아니다. 현재 기록만으로 운영 승격하지 않는다. 구현 시 원응답 영구 저장 → CPU 대기 → 최종 커밋의 상태를 분리하고, 원래 응답이 저장된 CPU 대기를 재개할 때 HCX를 다시 호출하지 않아야 한다. AntiSpoof 서비스는 한 번에 하나의 요청만 허용하므로 CPU 자체를 병렬 호출하면 안 된다.

독립 개선 우선순위는 HCX 동시2 비교 뒤다. CPU 중첩만으로 25분 완주를 기대할 근거는 없다. 반복된 전체 결과 재발행 비용을 줄이는 변경은 이번 범위 밖이며, 필요하면 체크포인트의 영구성·UI 진행 결과를 보존하는 별도 실험으로 검증한다.

재현 코드: `local-benchmark/phase1-speed-postprocess.cjs`. 완료 출력: `.runtime/phase1-speed-postprocess-v3/summary.json`, `timing.json`, `replay/`. 기존 디렉터리 재실행은 거부한다.

## 추가: 저장 응답 지연을 적용한 실제 CPU 중첩

전체 요청열의 시작부터 끝까지 균등하게 선택한 16묶음/163후보로 작은 중첩 실행을 추가했다. 샘플 인덱스는 결과를 보기 전 `[0,34,69,103,137,172,206,240,275,309,343,378,412,446,481,515]`로 고정했다. HCX 대신 원래 응답 시간만큼 기다렸다가 저장 원응답을 반환했다. AntiSpoof는 실제 CPU로 실행했다. 공통 모델 준비 6.51초를 비교 시간에서 제외하고 같은 persistent 서비스를 두 조건에 사용했다.

| 조건 | 작업열 완료 | 실제 CPU | 원응답·커밋 저장 |
|---|---:|---:|---:|
| 순차 | 73.363초 | 3.688초 | 0.291초 |
| 후처리와 다음 응답 대기 중첩 | 69.618초 | 3.647초 | 0.283초 |

**3.745초, 5.10% 감소**했다. 저장 응답 지연 합은 양쪽 69.157초로 같으며 16번의 모사 수신·163개 CPU 판정·커밋 순서가 모두 일치했다. 실제 네트워크 호출은 0이다. 원응답을 저장한 뒤 `saved-response → cpu-pending → committed`로 진행하며 다음 응답 대기만 먼저 시작한다. CPU 요청은 계속 직렬이다. 직렬화된 prepared/saved-response/cpu-pending/committed 네 상태에서 재개 행동을 검사해 수신·커밋 중복 방지 및 미확인 sent 재호출 거부를 확인했다. 이는 상태 분기 자체 검사이며 실제 프로세스 강제 종료나 운영 worker 재개 검증은 아니다.

이 작은 실행은 원래 전체 결과 재발행을 포함하지 않는다. 앞의 141초 반복 읽기와 혼합해 개선값으로 더하지 않는다. 실제 API·TPM·브라우저·25분 중단이 없는 고정 작업열 실험이므로 **운영 미채택, 후속 후보 보존**이 타당하다. 모델·정확도 변경 없이 일부 지연을 가릴 수 있으나 지금은 HCX 동시2의 기대 이득보다 작다.

코드 `local-benchmark/phase1-speed-postprocess-overlap.cjs`, 결과 `.runtime/phase1-speed-postprocess-overlap-v1/summary.json`; 각 arm의 원응답·판정·영구 ledger를 보존했다.
