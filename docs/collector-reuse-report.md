# 수집 파이프라인 재사용 검증 — 2026-09-23

**채택 완료:** Playwright와 Chromium 기반 headless Edge를 유지하고, 작업당 브라우저 프로세스 하나·URL마다 독립 context를 사용하는 수집 파이프라인을 운영 worker에 적용했다. 최종 v2의 사전 성능·근거 기준과 생명주기·전체 회귀·웹 연결 검사를 모두 통과했다. FIFO와 판정기는 유지한다.

## 실행 구조

FIFO로 다음 URL 선택 → 작업당 headless Edge(Chromium) 프로세스 하나 → URL마다 독립 BrowserContext와 페이지 생성 → 기존 요청 경계로 이동 → 제한된 DOM/네트워크 안정화 대기 → 제목·본문·작성자·댓글 및 삽입 iframe의 텍스트·스타일·좌표·문맥 일괄 추출 → 페이지/context 종료 → 기존 정규화·판정·체크포인트 → 다음 URL. 작업 종료 시 브라우저도 종료한다.

- 수집기: `agent/src/core/collect.cjs`의 `createCollector`와 `collect`. 기존 단독 collect 호출도 지원한다. 캐시·쿠키·localStorage를 공유하는 context 재사용은 하지 않는다.
- 운영 연결: `agent/src/worker.cjs`. 첫 URL을 읽을 때 생성하므로 브라우저 시작 시간이 scan 예산에 포함된다. 브라우저가 끊기면 남은 URL을 방문 실패로 소진하지 않고 partial 상태와 대기 목록을 보존한다.
- 시간 진단: 작업 산출물의 `collection-timing.jsonl`. 프로세스 시작/종료와 각 수집 호출의 page_create, navigation, readiness, extraction, context_setup, page_close, context_close 등을 기록한다. LLM 입력·근거 해시에는 시간 진단을 넣지 않는다. 과거 collection_elapsed_sec는 프로세스 시작/최종 종료를 제외하므로 성능 비교에는 사용하지 않았다.
- 기본 FIFO·네트워크 경계·대기 조건·의미 단위·광고 의도 판정·프롬프트·배치 크기는 유지했다. 브라우저 교체, 리소스 추가 차단, 병렬화, HTTP 수집 우회는 하지 않았다.

## 자료와 비교 방법

사전 기준은 `docs/collector-reuse-plan.md`. 기존 scope-site 두 개 전체 27/28페이지와 새 동작 진단 8페이지를 같은 순서로 비교한다. 3쌍씩 baseline→reuse / reuse→baseline / baseline→reuse. 한 버전당 18개 실행·378회 페이지 방문이며 원문뿐 아니라 후보 전체 구조, 정규화, 위치, 프레임 경로, 조상 스타일, 좌표, 문맥, 링크, 기법 signals, 수집 실패 기록을 비교한다. 가변 시간·수집 시각만 비교에서 제외했다. 정답은 사후 위치 채점에서만 사용한다.

변경 전 수집기는 `.runtime/collector-reuse-baseline/collect.cjs`에 고정했다. 시간 계측 코드와 원본의 10페이지 근거 일치도 별도로 검사한다. `.runtime/collector-reuse-v2/`에 최종 실행 소스, 해시, 쌍별 결과와 최초 회차 전체 스냅샷을 보존한다. LLM 실제 호출은 0회다.

## 결과

Windows, Node 24.19.0, Playwright 1.62.1, headless Edge 153.0.4234.48에서 측정했다. 아래 시간은 프로세스 시작·종료를 포함한 3회 중앙값이다.

| 자료 | 페이지 / 후보 | 페이지마다 프로세스 | 프로세스 재사용 | 감소 | 근거 차이 / 신규 누락 |
|---|---:|---:|---:|---:|---:|
| mixed-0 | 27 / 147 | 101.89초 | 41.93초 | 58.85% | 0 / 0 |
| mixed-1 | 28 / 150 | 104.51초 | 43.80초 | 58.09% | 0 / 0 |
| 새 동작 진단 | 8 / 22 | 22.94초 | 14.51초 | 36.73% | 0 / 0 |

세 자료군 모두 3쌍 중 3쌍 빨랐고, 3쌍 모두 근거가 동일했다. 최종 버전의 상위 URL 방문 378회, 후보 관측 1,914회(자료 1회당 319개)다. 기존 정답 광고 24개·정상 24개와 새 수집 대상 20개는 매번 모두 보존됐다. 아래에 적은 기존 누락은 여전히 남는다.

63페이지를 자료군별로 실행한 회차 전체의 wall time 중앙값은 **233.22초 → 99.82초, 57.20% 감소**다. 자료군별 중앙값의 합과 회차 합계의 중앙값은 서로 다른 집계이므로 수치가 조금 다르다.

| 구간 | 기존 | 재사용 |
|---|---:|---:|
| 브라우저 시작 | 30.37초 | 1.58초 |
| 페이지 생성 | 19.23초 | 16.14초 |
| 페이지 이동 | 5.31초 | 4.03초 |
| DOM/네트워크 안정화 | 69.39초 | 69.67초 |
| 근거 추출 | 1.85초 | 1.60초 |
| 브라우저 종료 | 104.58초 | 1.90초 |
| 별도 context 종료 | 브라우저 종료에 포함 | 2.49초 |

각 구간은 63페이지 합계의 3회 중앙값을 따로 구한 값이다. context 준비·페이지 닫기·직렬화 등은 위 간단 표에서 생략했으므로 표 합이 종단 시간과 일치하지 않는다. 전체 수치는 `.runtime/collector-reuse-v2/audit.json`에 있다.

반복적인 브라우저 시작·종료가 큰 비용이었다. 재사용 후 안정화 대기는 약 70%이며 근거 추출 자체는 작은 비중이다. 원문·스타일 수집을 줄이거나 대기를 단축하지 않아도 이득이 확인됐다.

**변동을 포함한 해석:** 기존 mixed-0 시간은 101.37/101.89/145.80초, 재사용은 41.93/40.36/42.60초다. 기존 방식 일부 종료에서 약 15.3초가 발생했고, 종료 지연의 내부 원인은 확정하지 않았다. 종료 처리는 기존 방식이 browser.close에 맡기고 재사용은 context를 명시적으로 닫는 차이도 포함한다. 특정 환경의 큰 종료 비용을 다른 장비/브라우저에서도 동일하다고 일반화하지 않는다. 기준선의 시작 비용만 보더라도 반복 프로세스 비용이 관측되며, 사전에 정한 중앙값·모든 쌍 비교 기준을 유지했다.

수집기·worker의 최종 소스는 측정 시작 때 보존한 파일과 바이트 해시가 일치한다 (`audit.json: source_unchanged=true`).

## 누락 및 일반화 해석

- 기존 두 사이트의 광고 24개·정상 24개는 원문과 정답 위치로 평가한다. 수집 도달을 광고 의도 정탐으로 간주하지 않는다.
- 새 진단의 20개 예상 수집 요소에는 분리 span 문장, 장문, 본문 밖 댓글, 조상 투명도, 음수 배치, 자모·유사문자, 지연 댓글, 같은/다른 출처 및 중첩 프레임, 저장소 격리 등이 포함된다.
- **기존 누락 유지:** 클릭해야 추가되는 댓글과 안정화 뒤 6초 타이머로 추가되는 댓글은 두 방식 모두 수집하지 못한다. 새 진단의 알려진 텍스트 대상 22개 중 20개 수집이며, 새로운 누락 0과 전체 수집 100%는 다르다. settled=true도 이후 변화가 없다는 보장이 아니다.
- **외부 CSS 차단 유지:** 다른 출처 CSS와 비GET 요청은 기존 계약에 따라 차단·기록한다. 실제 이용자 화면과 달라질 수 있고 재사용으로 해결되지 않는다. 일반 외부 링크와 삽입 iframe의 경계도 유지한다.
- 스크롤 아래 정상 문장을 음수 위치 광고로 추가 판정하지 않는다. 문자열·라벨·특정 URL 예외를 추가하지 않았다.
- 기존 자료는 반복 사용한 회귀 자료다. 새 자료도 같은 제작자의 합성 동작 진단이며 독립 실사이트 홀드아웃은 아니다. 실사이트 일반화, 장시간 메모리 사용, 실제 HCX 의도 F1·정밀도 개선은 이번 결과로 주장하지 않는다.

## 발견한 취소 오류와 보완

초기 v1은 시간·근거 기준을 통과했지만 별도 생명주기 검사에서 정지가 재현되어 그대로 채택하지 않았다. Playwright 로그에서 newPage가 진행 중일 때 context.close는 완료돼도 newPage 대기가 끝나지 않는 상태를 확인했다 (`.runtime/collector-debug.log`).

페이지 생성·이동·안정화 대기를 취소 신호와 함께 기다리도록 하고 context 종료 Promise를 한 번만 만든다. 취소되면 남아 있는 SDK Promise를 무한 대기하지 않고 정리한다. 특정 페이지/광고 예외 없이 I/O 취소 계약을 보완했다. 실제 운영 worker의 브라우저 강제 닫기 주입 후 대기 URL 보존과 새 프로세스 재개 결과도 비교했다. 이 수정 뒤 최종 v2를 다시 3쌍 반복했다.

v1과 v2는 Windows 실행 계정 경로도 달라 절대 시간을 합산하지 않는다. 각 버전 안의 쌍별 비교를 사용하며, 최종 채택 수치는 v2만 사용한다. 시작·종료 비용은 장비와 실행 환경에 의존한다.

## 검증 명령

최종 실행에서 아래 검사를 모두 통과했다. 상세 로그는 `.runtime/collector-reuse-v2/validation.log`다.

- 생명주기: 원본 근거, 404 후 회복, 취소 후 재수집, 사전 취소, 대기 상한, 리다이렉트, 선택적 기법 관찰, 체크포인트 재개.
- 실제 worker Mock: 3페이지에 브라우저 시작/종료 각 1회, 저장소 격리, 두 번째 context에서 브라우저 강제 닫기 주입, 미방문 2 URL 보존, 새 프로세스 재개 후 후보·판정 동일.
- 기존 전체 Agent: 자모 22,344개 왕복·경계, 수집 의미 단위, 70개 기법 대상, 문맥·귀속·판정 계약, 반복/예산/강제 종료 재개 검사 등 기존 테스트 전체.
- 범위 검사: 동일 출처 다른 경로·쿼리, 외부/중첩/srcdoc iframe, 댓글, 순환, 실패, 페이지/시간/호출/후보 예산, 부분 결과, 재개 및 과거 6조건 순서 보존.
- 웹 Mock: React→Spring Boot→변경된 worker→진행 상황·결과 다운로드, 취소, 시간/페이지 예산 부분 결과, 모바일 화면, 백엔드 재시작 후 이력 보존. `.runtime/verification-1790151497332/report.json` 참고. `scripts/verify-web.cjs`는 기존 사용자 작업을 건드리지 않도록 별도 app-root와 작업 저장소를 사용한다.

프로젝트 루트에서 실행한다. 모두 유료 API를 사용하지 않는다.

```powershell
node agent/experiments/collector-reuse-run.cjs .runtime/collector-reuse-NEW
npm.cmd run test:collector --prefix agent
npm.cmd test --prefix agent
node agent/scope.test.cjs
node scripts/verify-web.cjs
```

첫 명령은 새 출력 폴더와 원본 baseline 파일이 필요하다. scope-site 전용 loopback 포트 18984~18986을 사용한다. 성능 비교 도중 다른 브라우저 검사나 빌드를 함께 실행하지 않는다.
