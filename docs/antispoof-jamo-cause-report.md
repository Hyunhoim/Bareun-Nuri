# AntiSpoof v1.0 순수 자모의 HOMOGLYPH 오확정 원인 진단

2026-09-30. 운영 모델을 동결하고 270행 정보 대조와 216행 표시 구간 대조를 실행했다. 학습/API/운영 코드 변경/최종 평가 재실행은 모두0이다. 이 자료는 원인 진단이며 실제 공공사이트 오탐률이나 독립 일반화 평가가 아니다. 486행을 독립 사례486개로 해석하지 않는다(한글9어휘, 문맥·표기 파생).

## 직접 관찰한 원인

**이번 재현 오류는 순수 자모를 항상 H로 분류하는 오류가 아니라, 주변 치환과 표시 구간의 기법을 혼동하는 현상이다.** 표시한 자모·Unicode 근거·제목은 고정하고 옆 문자열만 바꿨다.

|판정대상 표시|H present 모델 점수|결과|
|`[표기]ㅎㅏㄱㄱㅛ[/표기]`|1.31%|J만 확정|
|`[표기]ㅎㅏㄱㄱㅛ[/표기] coral`|1.80%|J만 확정|
|`[표기]ㅎㅏㄱㄱㅛ[/표기] c0ral`|99.59%|J와 H 동시 확정|
|자모를 표시한 모집 문장|0.28%|J만 확정|
|자모를 표시한 교육 문장|0.16%|J만 확정|

위 수치는 모델 softmax 점수이며 실제 정확도의 보정 확률이 아니다. 자모를 못 읽거나 광고 문맥만 보아서 일어난 것으로 설명하기 어렵다. 같은 입력으로 실행했던 worker의 오류도 재현했다.

추가 대조는 학습/개발/진단 한글 각3어휘 × 영문6어휘의54조합이다. `4lpine`, `cypr3ss`, `b4dger`, `d0lphin`, `3merald`, `falc0n`을 원래 영문과 짝지었다. 글 전체에 분해 자모와 치환이 함께 있을 수 있으므로 표시 구간별 정답을 다르게 정의했다.

|표시 구간/옆 내용|J확정|H확정|구간 정답과 일치|
|자모만 표시, 옆은 일반 영문|54/54|1/54 오확정|53/54|
|자모만 표시, 옆은 숫자 치환|54/54|23/54 오확정|31/54|
|숫자 치환만 표시, 옆은 자모|0/54|0/54, 모두 H보류|0/54|
|자모와 숫자 치환을 함께 표시|54/54|54/54|54/54|

H오확정23개는6종 치환 모두에서 관찰됐다. 단순히 특정 학교/c0ral 문자열만의 현상은 아니다. 다만 작은 합성 대조이므로 실사이트 빈도와 모든 자모 유형으로 확대하지 않는다. 숫자 치환만 표시할 때의 보류는 원래 식별자/문맥 부족 문제도 섞일 수 있어 전부 대상 귀속 오류라고 단정하지 않는다.

## 학습·입력·임계값 감사

1. **잘못된 순수 자모 gold는 이번 감사에서 발견되지 않았다.** 후속 학습에 들어간 base+extra의 순수 compat156/NFD156/부분156/공백64/제로폭64행, 총596행은 모두 J present/H absent다. 학습의 silver계열 제외 기준을 따랐다. 전 어휘의 정답 의미까지 사람 검수했다는 뜻은 아니다.
2. **표시 구간 대비 학습의 공백이 확인됐다.** 복합156행은 분해 자모와 영문 치환을 하나의 `[표기]...[/표기]`에 넣고 J/H 모두 양성이다. 운영은 각각 다른 표시 구간으로 판정한다. 같은 전체 문장에서 표시 구간만 자모/치환/둘 다로 바꾸는 대조가 생성기에 없다. 이는 경계 실패의 유력한 학습 원인이다. 원인을 유일하게 확정하려면 이런 자료 보강만 바꾼 재학습 대조가 필요하다.
3. **낮은 H임계값은 증폭 요인이지만 주원인은 아니다.** 54개 숫자 옆 자모에서 argmax만으로도20개 H오확정, .20 보정 시23개다. 최초 학교 예시도 argmax부터 H였다. 임계값 변경만으로 경계 문제를 해결할 수 없다.
4. **Unicode 근거의 존재 자체가 위장 정답은 아니다.** 학교 자모의 대응은 `ㅎ→ᄒ`, `ㅏ→ᅡ`, `ㄱ→ᄀ`, `ㅛ→ᅭ`이며 이 표는 자모 표현 차이도 포함한다. 같은 근거의 단독 입력에서는 H가 낮으므로 표 자체만으로 오류가 발생한다고 단정하지 않는다. 그러나 서로 다른 대응 종류를 한 문자열로 제공하는 구조는 혼동 여지가 있다.
5. **Unicode 근거를 없애는 해결은 위험하다.** 9어휘×2자모형태×5문맥=90개는 Unicode가 있을 때 모두 J확정, 없으면 J확정0이었다. 제거 입력은 학습 분포 밖 개입이므로 실제 배포 정확도 하락90개로 해석하지 않는다. 다만 무검증 제거의 근거는 없다. NFD 표기90파생행은 tokenizer 원표기에 UNK가 있었고 호환 자모에는 없었다. 학교 오류 입력 역시 UNK가 없다. NFD 토큰화 한계가 이번 호환자모 오류의 직접 원인은 아니다.
6. **모델은 구간 전용 출력 구조가 아니다.** 설치된 transformers4.57.3 ElectraClassificationHead는 첫 토큰 표현으로 문장 분류한다(`modeling_electra.py:819`). `[표기]`는 학습한 텍스트 표시이며 hard attention mask가 아니다. 대상별 판단을 학습할 수 있지만 현재 구조가 물리적으로 주변 증거 혼입을 막아 주지는 않는다.

## 권장 개선 순서

### 1. 대상 구간 귀속 대조를 중심으로 재학습

같은 전체 문장을 두고 표시 구간만 바꿔 J전용/H전용/J+H/둘다아님 정답을 부여한다. 옆 요소에 기법이 있어도 대상의 정답은 유지하고 대상 내부에 실제 다른 문자 치환이 있으면 둘 다 허용한다. 문장 순서·거리·댓글 작성자·숫자 밀도·제목/본문·원래 식별자를 교차한다. 운영과 동일한 구간 선택 및 문맥 포장을 사용한다.

현재 학교/c0ral 등 진단 문구를 그대로 훈련하지 않는다. 출처·어휘·생성틀·원문 파생 그룹을 분리한 새 학습용 문구를 만들고 현재 자료는 회귀로 남긴다. 기존 J/H 기초자료도 재학습에 섞어 망각을 확인한다. 첫 비교는 설정/가중치 출발점을 고정하고 자료 보강만 변경한다. 이 방향을 1순위로 권한다.

### 2. Unicode 근거의 종류를 구분하는 입력 개선을 별도 비교

자모 조합/정규화 관계와 다른 문자·숫자 치환 가능성을 별도 필드로 제시한다. 원문과 주변 문맥은 유지한다. 현재 동결 모델의 입력 형식만 갑자기 바꾸지 말고 동일 학습량의 대조로 검증한다. 필요하면 모델 H확정의 근거가 표시 구간 내부에 존재하는지 코드로 점검하고, 근거가 없으면 부재 확정보다 검토 대상으로 남긴다. Unicode 표에 없는 숫자 대응도 있으므로 표에 없다는 이유만으로 H를 일괄 부정하지 않는다.

### 3. 위 보강으로 부족할 때만 대상 구간 표현을 쓰는 판정층

문장 첫 토큰뿐 아니라 표시한 구간의 토큰 표현을 이용하는 head를 비교한다. 주변 의미는 식별자 판별에 필요하므로 전부 삭제하지 않는다. 새 모델 교체보다 현재 encoder에서 구간 귀속을 강화하는 실험이며 속도·RAM·보류 부담을 함께 측정한다.

`JAMO이면 HOMOGLYPH 금지`, Unicode 전체 삭제, .20 임계값만 올리는 방식은 우선 권하지 않는다. 실제 복합 기법 손실이나 자모 인식 회귀, 기존 숫자 치환 누락 증가 가능성이 있다.

## 채택 검증 기준

개발에서 구간 밖 H의 오귀속 감소와 구간 안 H/J 정탐 보존을 함께 확인한다. HCX 양성 저장 입력의 기존 정탐 손실·새 FP·기법별 F1·보류·CPU지연을 비교하고, 유망할 때25분 종단 조건을 적용한다. 문장 전체에 H가 있다는 것과 정확한 구간에 H를 붙였다는 것을 구분한다. 이번 진단 결과를 실제 광고 누락률이나 운영 F1로 보고하지 않는다. 현재 운영은 사용자 채택 v1.0 그대로 유지했다.
