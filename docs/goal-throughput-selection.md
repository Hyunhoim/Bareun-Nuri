# 처리량 개선 후속 검증 선택 기록

2026-09-25. `goal-throughput-plan.md`의 기준을 유지한다. 운영 소스는 아직 변경하지 않았다.

## 실제 호출 전 선택

- cap-only 기존104개 ABBA는 각44TP/2FP/4FN이며 네 조건의 전체 판정이 동일하다. 3072 평균132.03초,512 평균52.47초로 후속64개에 진입한다. 실제토큰은 각39,733으로 같고 비용절감은 아니다. 저장 재생 작업 일부가 동시에 실행되어 장비 부하 통제는 완전하지 않았으나, 요청 대기79초 안팎이 거의0으로 줄고 서비스시간은52~54초로 유지됐음을 따로 확인했다.
- 기존21페이지 저장근거/300회 모의 호출에서 운영은4페이지/광고판정기회0개, RR2는4페이지, RR8은14페이지/광고판정기회6개, SRPT8+8턴 대기보호는15페이지/광고판정기회8개였다. 전체광고 분모28, 통제위치64다. 모의 정상 응답의 F1은 의미 성능 근거가 아니다.
- SRPT8을 실제 비교 후보로 선택한다. 개발자료 결과를 보고 선택한 것이므로 같은 자료에서의 추가결과를 독립 일반화 증명으로 쓰지 않는다. 매개변수8은 사전계획 그대로이며 페이지 유형/광고signal/정답을 스케줄 입력으로 사용하지 않는다. 선택하지 않은 정책을 기본 경로에 연결하지 않는다.
- 저장쓰기 감소와 RSS 감소는 구분한다. 기준선 체크포인트 누적39.69GB 대비 SRPT8은167.43MB지만 샘플 RSS는220.8MB 대비433.0MB로 증가했다. 둘 다768MiB 보호 아래였다. 입력 전체를 계속 메모리에 보관하지 않더라도 JSON 파싱과 GC 순간 비용은 남는다. 시간333.33/36.34초는 모의 저장제어 시간이며 동시 작업 부하 차이가 있어 실제 모델 지연 비율로 쓰지 않는다.
- 81페이지615후보 완주 재생에서 근거/관찰/최종집합은 같았지만 페이지별4개 배치의 잔여처리로154→201회 호출이 필요했다. 이 회귀를 숨기지 않으며 실제 시간·정탐 이득이 상쇄하는지 평가한다.

## 새 스케줄 검증 자료

`.runtime/goal-scheduling-site-v1`은 루트+15페이지, 본문단위8/40/160개 각각5페이지다. 수집 후1141후보(광고32/정상1109), 통제64위치와4종관찰64개가 보존됐다. 긴 광고 앞/중간/끝을 포함한다. 생성·봉인 후 모델결과에 맞춰 수정하지 않는다.

qa-v1에서 gold의 `#id`와 collector의 `tag#id` 문자열비교 오류가 있었다. 원본 HTML의 ID유일성·태그를 검증하는 대응만 QA도구에 추가했고 qa-v2는 같은 저장16snapshot을 재사용했다. 사이트/정답/원문/수집근거는 불변이다. 이 변경은 수집성능 개선이 아니다. 실시간 비교에서는 qa-v2의 전체 라벨과 통제64를 각각 보고한다.

이 자료는 정적 합성 스케줄 검사다. 실제 사이트 언어·동적 댓글·iframe 일반화 증거로 확대하지 않는다. 광고32개 전체 분모를 유지하며, 미방문·미판정도 누락이다. 기존 복제본은 정답 밖 실제 텍스트의 양성을 별도 검토한다.

## 실행

`agent/experiments/goal-live-run.cjs`는 실제 current core를 baseline/cap으로, 별도 bounded runner를 srpt8로 실행한다. 운영 worker와 같은4개 fitBatch/계약을 사용하며 실제 request의4개상한도 검증한다. 동일25분/200페이지/300호출/768MiB/토큰보호를 적용한다. 기준선과 후보는 순차 실행한다. source hash·원요청/응답·중간근거·판정·coverage를 보존하고 미확인 요청은 자동 재전송하지 않는다. 통합 후보는 저장+스케줄+이미 분리검증한 cap의 결합이므로 순수 스케줄 효과라고 말하지 않는다.

## 새64 결과 후 진단 결정

새64 ABBA에서 A1/A2는30TP/2FP/2FN, B1은30/3/2, B2는30/2/2다. 평균F1은93.75→93.03%, 정밀도93.75→92.33%, 재현율93.75%동일이다. 엄격한 새자료 비감소는 미통과이므로 cap512의 단독 운영 승격을 보류한다. 작은 표본의 반복변동을 확인하기 위해 사전계획에 있던615회귀 A/B를 실행한다(308회/예약250만/1시간,예상예약1,207,853). 새64의 실패문구를 보고 cap 수치나 프롬프트를 튜닝하지 않는다. 기존회귀의 개선이 있더라도 새64의 평균하락을 없던 것으로 해석하지 않는다.

cap이 채택되지 않으면 실제 배분 비교는 `srpt8-3072`로 기존 출력상한을 유지할 수 있다. 이는 미채택 요소를 결합안에 자동 포함하지 않기 위한 독립 경로다. 실제 실행 전에 어느 조건을 사용하는지 기록한다.

별도 API0 quota 재생에서는52k→57k의 예상 이득이 약3%라 추가유료 검증/운영반영을 하지 않는다. 실제 응답 헤더는60k/60QPM이었다. [공식 이용량 정책](https://guide.ncloud-docs.com/docs/clovastudio-ratelimiting)의 TPM은 입력+최대출력 기준이고 계정단위로 합산된다. 실제출력으로 예약을 임의 환급하는 방식은 적용하지 않는다. 근거는 `.runtime/goal-quota-replay-v1`에 보존했다.

## 615 완료 후 실제 비교 고정

615 판정은 A/B 완전 일치(38TP/14FP/5FN), 시간830.743→330.606초다. 신규64의 평균회귀 때문에 cap512는 계속 보류한다. 후속 실제 비교는 baseline 대 srpt8-3072로 고정하며 출력상한3072/동일 의미계약을 유지한다. 먼저 신규 scheduling 사이트에서 순차 비교하고, 유효성 확인 후 실제 DOM 복제본에서도 비교한다. 전체 광고 분모·기존 정탐 손실·정밀도·시간·호출·RSS를 함께 보고한다. 이번 변경은 저장 및 배분의 결합이며 의미 프롬프트 개선으로 해석하지 않는다.
