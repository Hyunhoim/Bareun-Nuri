# Gemini 3.5 Flash-Lite / Gemma 4 E2B 비교

2026-10-01. **현재 HCX-007 운영을 유지한다.** Gemini는 이번 자료에서 HCX에 가까운 광고 의도 정확도를 보였으나 더 느렸다. Gemma는 기존 Kc 광고 의도 분류기보다 정확했지만 CPU 속도와 정확도를 동시에 만족하는 HCX 대체 근거는 얻지 못했다. 운영 코드 변경·추가 학습·Phase 2 사용은 없다.

## 조건과 범위

- 기존 저장 입력 221개를 그대로 사용했다: 광고 64, 정상 120, 근거 부족 37. 정상에는 사용자가 검수했던 실제 정상 자료 17개가 포함된다. 나머지는 이미 관찰한 합성 개발·회귀 자료다. 독립 최종 평가가 아니다.
- 광고 F1은 정답이 확정된 184개에서 계산한다. 근거 부족 37개는 별도 평가한다. 처리시간은 221개 전체다. 광고 의도만 비교했으며 **4종 기법 F1이나 수집·탐색을 포함한 운영 전체 F1이 아니다.**
- 공통 대상·문맥·4분류 지시를 사용했다. 단일 후보 또는 자료군별 최대 12개 묶음, 동일 순서다. 같은 원문에서 파생한 자료와 같은 문장틀이 포함되어 있고, 묶음 내 대조 사례의 영향도 배제하지 못한다.
- HCX-007: none, 출력 512, seed 42, 현재 12개 묶음 20회 재측정. 과거 결과도 보존했다.
- Gemini: 실제 API 모델 `gemini-3.5-flash-lite`, minimal, temperature 0, 출력 512, JSON Schema. minimal은 HCX none과 동일한 설정은 아니다. 응답에서 보고된 추가 추론 토큰 합계는 0이었다. seed는 지정하지 않았다.
- Gemma: 공식 `google/gemma-4-E2B-it-qat-q4_0-gguf`, QAT Q4_0, 추가 학습 없음. llama.cpp b11284, CPU 8스레드, GPU/추론/프롬프트 캐시 비활성화, 컨텍스트 16,384. 출력은 단일 32·묶음 512다. 모델 파일 해시를 검증했다.
- Kc: 기존 `.runtime/kcelectra-freeze-v1/full/model` 광고 의도 분류기, CPU FP32·8스레드·추론 배치 8. **운영 AntiSpoof 기법 모델과 다르다.**

API 시간은 요청부터 응답 본문 수신까지의 합계이며 로컬 호출 간격 대기·수동 점검 중단은 제외했다. Gemini 단일에는 호출 제한을 위한 대기 190.84초가 추가되어 응답+대기는 1,111.63초다. 중단 후 재개 사이의 점검 공백은 이 값에도 포함하지 않았다. 12개 묶음은 Gemini 대기 0.18초, HCX 대기 0.001초 미만이었다. Kc는 인코딩 0.045초·모델 로딩 0.210초가 별도이며 Python 시작 시간은 제외했다. Gemma의 로딩·형식 검사용 호출도 표에서 제외했다. 한 장비·한 번의 순서별 측정이므로 지연의 보편적 배율을 확정하지 않는다.

기존 HCX 12개 기록은 36.13초·F1 99.21%였다. 이번 39.24초 재측정과 광고/정상 판정은 221개 모두 같았고, 비광고 하위 라벨 등 4분류 판정은 3개 달라졌다. 과거 HCX 단일은 F1 91.43%, 응답 151.37초·대기 109.51초였다. 이 단일 값은 이번 실시간 재측정이 아니다.

## 주요 차이

**Gemini와 HCX의 F1 소수점 차이는 개선 근거가 아니다.** 확정 정답에서 양쪽 오류는 각각 1개다. Gemini는 HCX가 놓친 짧은 권유를 회복했지만, 피해자가 인용한 판매 문구를 새로 광고로 판단했다. 이번 묶음 응답 시간은 HCX의 약 3.03배였다.

**Gemma는 묶음으로 빨라졌지만 정확도가 떨어졌다.** 단일 대비 약 56.7% 시간을 줄였으나 FP 5→10, FN 2→5다. 특히 대상·주변 문맥의 귀속을 보는 44개 자료에서 광고 F1이 100→75.86%로 하락했다. 피해 설명을 실제 권유로 오인하거나, 정상적인 서두·상담 게시판 문맥에 붙은 실제 광고를 정상/인용으로 처리했다. 묶음 간섭과 문맥 처리의 약화가 원인 가설이며 모델 용량 한계로 확정하지 않는다.

단일 Gemma의 누락 2개는 같은 짧은 도박 권유 원문의 서로 다른 문맥 변형이다. 이를 독립적인 두 종류의 실패로 부풀리지 않는다. 예방 설명·신고 문구의 오탐도 남는다.

## 근거 부족과 Kc 입력 길이

| 모델·조건 | 근거 부족 37개 중 보류 정답 | 광고로 확정 |
|---|---:|---:|
| HCX 이번 12개 | 19 | 6 |
| Gemini 12개 | 12 | 15 |
| Gemma 단일 | 4 | 2 |
| Gemma 12개 | 3 | 6 |
| Kc | 2 | 22 |

이 37개는 위 광고 F1의 정상 표본에 포함하지 않았다. 따라서 F1만 보고 불확실성 처리까지 좋다고 해석해서는 안 된다. 보류하지 않았다고 모두 광고로 판정한 것은 아니며, 나머지는 정상/인용 등으로 확정했다.

Kc 입력 221개 중 4개가 789~922토큰으로 512 한도를 넘었다. **4개 모두 정상 정답을 유지했다.** 이번 FP 44개·FN 3개는 이 4개의 잘림으로 설명되지 않는다. 모델 설정의 `max_position_embeddings`도 512이므로 tokenizer 상한만 올리는 것으로 긴 문맥 처리를 보장할 수 없다. 다른 운영 자료의 잘림 위험까지 없다는 뜻은 아니지만, 이번 오류를 개선하기 위한 첫 수단으로 토큰 확대를 지지하지 않는다.

## 실행 결함·한도 처리

Gemma 최초 comparison-v1은 llama.cpp README의 평면 `response_format.schema` 예시를 따랐다. b11284 실제 구현은 `type: json_schema`일 때 `response_format.json_schema.schema`를 읽어, 최초에는 일반 JSON만 강제됐다. 묶음 20회 중 10회에서 숫자 문자열이 나왔으며 이 결과를 모델의 스키마 준수 능력으로 평가하지 않는다. 원기록·당시 소스를 보존한 뒤 올바른 중첩 구조로 단일/묶음을 모두 다시 실행했다. 최종 comparison-v2는 지시와 충돌하는 고정 스키마 검사도 통과했고, 241회 모두 형식 오류·출력 잘림이 없었다. 원문을 숫자로 임의 변환해서 점수를 복구하지 않았다.

Gemini 48번째 요청에서 무료 쿼터 분당 15회 제한의 명시적 HTTP 429를 받았다. 47개 성공 응답은 재호출하지 않았고, 거절이 확인된 요청부터 별도 디렉터리에서 4.6초 간격으로 이어갔다. 응답 여부가 불명확한 요청을 자동 재시도하지 않았다. 총 242회 시도 중 성공 241회·429 1회, 형식 실패·안전 필터 차단 0회다. 총 103,411토큰(입력 100,480·출력 2,931)을 보고받았다. HCX 신규 호출은 20회다.

Gemini의 공식 일반 유료 단가를 기계적으로 적용하면 이번 성공 호출 합계는 약 $0.0375, 12개 묶음 조건만 약 $0.0113이다. 이는 청구액 조회가 아니라 비교용 환산이다. 여러 후보를 한 요청에 넣은 이번 묶음은 별도의 비동기 Batch API가 아니므로 일반 단가를 사용했다.

Gemma 프로세스 최대 Working Set은 약 2.72GiB, 모델 파일은 약 3.35GB였다. 전체 시스템·브라우저까지 포함한 배포 최소 RAM 수치가 아니다. 실행 후 모델 서버를 종료했다.

## 판단과 검증 범위

- **운영: HCX-007 12개 묶음 유지.** 이번 비교에서 정확도·속도 균형이 가장 좋다.
- **Gemini: 대체 API 연구 후보로 보존.** Kc보다 정확하지만 이번 설정에서는 HCX보다 빠르지 않았고, 불확실성 처리도 더 좋지 않았다. 무료 이용 가능성만으로 운영 교체하지 않는다.
- **Gemma: 현재 CPU 대체안 미채택.** 단일은 정확도가 비교적 좋지만 느리고, 묶음은 정확도 손실이 크다. 추가 파인튜닝으로 HCX를 넘을 것이라고 예측할 근거는 없다.
- Phase 2는 평가/학습 모두 0회이며 manifest 해시가 보존됐다. 새 독립 평가·25분 운영 평가·기법 모델 변경은 하지 않았다. 같은 자료에 맞춘 프롬프트/학습 튜닝도 하지 않았다.
