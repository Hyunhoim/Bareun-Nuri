# 동일 전체 작업량의 배치4 대 배치8 진단

2026-09-26. API0, 운영 변경0. 실행 전 고정된 기존20페이지의3557판정작업을 끝까지 분할하는 계산이다. 실제25분 실행 결과나 정확도 측정이 아니다.

## 변경 요인

운영 C의 `splitCandidate`, `judgment.contract`, `fitBatch` 및 실제 createSession 기반 요청 추정기를 그대로 사용하고, 페이지별 최대 요청 크기만4→8로 바꿨다. 출력512·HCX none·52,000TPM 예약 한도는 유지했다. 페이지 간 후보를 섞거나 문맥을 삭제하지 않았다.

| 항목 | 최대4개 | 최대8개 |
|---|---:|---:|
| 전체 원본 후보 |3543|3543|
| 장문 분할 후 작업 |3557|3557|
| 전체 작업 완료에 필요한 호출 |899|458|
| 요청 예약 토큰 추정 합계 |2,870,953|2,250,293|
| 고정 출력 예약 합계 |460,288|234,496|
| 최대 단일 요청 예약 추정 |49,631|51,570|
| 52k 때문에 제안보다 축소한 배치 |1|2|

호출은49.05%, 예약 추정 합계는21.62% 감소했다. 최대8 조건의458콜은600호출 상한보다 적지만, 이를25분 완주 가능성으로 바꾸어 말할 수는 없다. 예약 추정은 실제 제공사 토큰과 다르고, API 지연·사용량 창 대기·수집·저장 시간이 포함되지 않는다. 512에서8개 출력이 잘리지 않는지도 실제 응답으로 확인해야 한다.

## 보존 검사

- source는 `.runtime/scale-large-live-v1/snapshots`의20파일이다. 후보 배열은 원래 `.runtime/jamo-context-live-c-v1/snapshots`와 deep equality를 통과했다. 양쪽 전체 후보 SHA256은 `26f456a5ec7de05dc71e7c84fcb016e332808799f3020c17de59c36215327c56`이다.
- 전체 후보·문맥·관찰 근거가 들어 있는 snapshot 해시는 실행 전후 동일하다.
- 두 분할 조건에서3557작업의 순서/ID가 원본 페이지별 작업열과 완전 일치하며 각 ID는 정확히1회 포함된다.
- 후보별 모델 initialEvidence 해시가 두 조건 모두 `70380afa28931e0c1c9c6d5eec0a140c47d3e6d76def32cd00d1f1322244febe`로 같다. 원문/문맥/링크/복원읽기는 동일하다. **배치 동료가 바뀌므로 모델 판정까지 동일하다는 뜻은 아니다.**
- 장문5개는 각각3/5/3/3/5개 구간이다. 첫 시작0, 마지막 끝=원문길이, 인접400자 overlap, 원문 slice와 정확 일치를 검증했다.
- fitBatch가 줄인 나머지 후보는 다음 요청으로 넘어가며 전체 작업 ID 검사로 유실이 없음을 확인했다. 요청예산을 맞추려고 내용을 잘라내지 않는다.

재현 코드 `agent/experiments/throughput-batch8-diagnostic.cjs`, 결과 `.runtime/throughput-batch8-v1/audit.json`. 원래 결과 디렉터리가 존재하면 덮어쓰지 않고 종료한다. wire ID 축약 모듈은 사용하거나 수정하지 않았다.

## 한계와 판단

이는 페이지 내부 전체 완료 작업의 분할 계산으로 실제 SRPT8/aging8 선택 순서 및25분 경계와 다르다. 자연 링크 발견·원격 수집·의미 판단·출력 잘림·재개를 시험하지 않았다. 기존 관찰 자료이므로 새 홀드아웃 일반화도 아니다.

요청 수와 공통 프롬프트 반복을 크게 줄이는 근거는 확인돼 배치8은 제한 실제 비교 가치가 있다. 과거 배치 변경에서 문맥 간섭과 판정 회귀가 있었으므로, 실제 광고정탐/정상오탐/출력512 완전성 관문을 통과하기 전 운영 확대 근거로 쓰지 않는다. ID단축이나 추가 입력 변경을 혼합하지 않아 각 요인의 효과를 분리한다.
