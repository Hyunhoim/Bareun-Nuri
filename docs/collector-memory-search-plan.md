# 4GiB 미만 수집 동시 수 탐색 계획

2026-09-30 사용자 후속 요청: 메모리4GiB를 넘지 않고 기존 수집 근거를 보존하는 가장 빠른 동시 수를 찾는다. 운영 반영은 별개다. API/외부기관 요청0, 기존 HCX/수집기 코드 변경0.

## 지표와 보호

- 측정 메모리는 생성 시각을 검증한 수집기 Node·브라우저·측정 PowerShell의 working-set 합. 부모의 자료 제공 서버는 제외한다. 공유 페이지 중복 가능성이 있어 물리 RAM 필요량과 다르다.
- 모든 조건을 같은500ms 휴지 간격으로 표본화한다(CIM 조회 시간은 추가됨).3.75GiB 표본에서 수집을 취소한다.4GiB 미만을 채택 조건으로 하며 중단 조건은 성공에서 제외한다. 표본 사이 순간 상승을 완전히 보장하는 OS 하드 제한은 아니다. 측정 오류/메모리 미측정도 통과시키지 않는다.
- 페이지당 기존 안정화·최대 노드·문맥·기법·iframe·FIFO 묶음/출처/쿼리·독립 context·브라우저 재사용은 유지한다. 중단/실패/미수집은 그대로 남긴다.

## 자료와 사전 탐색 순서

- 기존 부산 DOM 복제본의 성공 페이지63개 전체를 사용한다. 실제63개 주소이며20페이지를 복제해 고유 표본 수를 늘리지 않는다. 모두 기존 dev 자료이며 새 홀드아웃이 아니다. 각 조건은 새 Node 프로세스에서 같은 URL 순서로 끝까지 수집한다.
- 기준선20개를 먼저 수집한다. 이후 거친 탐색은5/10/15/25/30/35/40 각1회다.25 이상에서 메모리 보호 중단이 발생하면 더 큰 수는 실행하지 않는다. 처리 실패/근거 변경 조건은 통과시키지 않고 원인을 보고한다.
- 기준선20개가 메모리 보호로 중단되면5개를 전체 근거 참조로 사용하며20개 이상은 추가 확대하지 않는다.5개도 완주하지 못하면 탐색을 중단해 환경/자료 한계를 보고한다.
- 위 통과 조건 중 가장 빠른 설정을 중심으로 ±4의 정수 동시 수를 추가1회 검사한다(5~40 범위, 이미 실행한 값 제외, 메모리 중단 수 이상 제외). 서로 다른 동시 수 탐색은 최대16개다. 이는 제한된 탐색 범위 내 최적 후보이며 모든 가능한 수/사이트의 전역 최적 증명이 아니다.
- 탐색에서 빠른3개와 기준선20개(중복 제거)를 고정한 뒤 각3회 추가 확인한다. 확인 순서는 회차별 순환한다. 선택은 확인3회 모두 메모리4GiB 미만/보호중단0/측정오류0/기존근거손실0인 조건의 벽시간 중앙값 최저다. ‘5% 이내 더 작은 수’ 규칙 대신 이번 사용자가 지정한 가장 빠른 조건을 선택한다. 근접·반복 변동은 함께 보고한다.
- 최종 후보와20개 기준선을 기존 동작8페이지 및 두 합성사이트20초 탐색에서 각2회 비교한다. 기준선 근거·광고 위치 손실0/메모리 조건을 확인한다. 순위는63페이지 확인 결과이며 자연 탐색이 더 느리면 함께 보고한다.8페이지의 실제 동시 수 상한8은 명시한다.
- 전체 최대40실행,1시간 안전 상한. 고정 URL 실행당600초/프로세스630초, 탐색20초/프로세스60초. 중단 시 전체 완료로 보고하지 않는다. 동시 수 선택에 정답 라벨/URL별 예외를 사용하지 않는다.

## 해석

‘누락0’은 같은 수집기의 전체 수집 기준선 대비 원문·문맥·위치·스타일·링크·프레임·기법 근거 보존이다. 원래 클릭/6초 댓글 및 수집 한도 등의 미검사까지 해결됐다는 의미가 아니다. 해당63페이지에 맞춘 선택 가능성과 실사이트 서버·대규모/동적 페이지·25분 HCX·운영 재개 미검증 범위를 공개한다. 데이터·실행 소스·시간·자원·선정 과정·탈락 사유를 보존한다.
