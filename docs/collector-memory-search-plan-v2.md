# 4GiB 미만 탐색 재설계: 완료 원본 해제

2026-09-30. 이전 [사전 계획](collector-memory-search-plan.md)의 v1은20개가23/63페이지,5개가55/63페이지에서 보호 중단되어 완료 기준선을 확보하지 못했다. 최대 작업 메모리 합은각3.94/4.04GiB로,5개는3.75GiB 감지 후 정리 중4GiB를 넘었다. 실패 원본은 `.runtime/collector-memory-search-v1`에 보존하며 성공/속도 순위로 사용하지 않는다.

운영 bounded-scan은 원본을 디스크에 저장하고 해제하지만 기존 비교 실행기는 완료한 snapshot 전체를 rows에 계속 유지했다.5개 중단 표본은 Node1.02GiB/브라우저2.89GiB였으며 보관만이 유일한 원인이라고 단정하지 않는다. 원본 저장·해시·탐색 링크 반영 후 완료 snapshot 참조를 놓는 실험 옵션을 모든 조건에 동일 적용한다. 근거는 삭제/축약하지 않고 디스크에 보존한다. 운영 코드는 바꾸지 않는다.

- 메모리 정의는 수집기 Node·브라우저·측정기 작업 메모리 합, 동일한 생성 시각 검증/500ms 휴지 표본. 보호 기준3.25GiB, 성공 기준4GiB 미만·보호 중단0으로 여유를 늘린다. 표본 사이 순간 최고치의 OS 하드 보장은 아니다.4GiB 초과가 관측되면 즉시 보고하고 해당 설정을 제외한다.
- 기존 부산 성공 DOM63페이지 전체, 새 프로세스·동일 순서·동일 대기/추출/격리/FIFO. 완료 snapshot을 해제하므로 이전 메모리 보관 방식의 속도와 섞지 않는다. 새 학습/의미 평가/외부 요청/API 없음.
- 동시5 전체 기준선을 먼저 확보한다. 보호 중단되면1개를 참조로 사용하고5 이상 확대를 중단한다.1개도 실패하면 탐색을 중단한다.
- 거친 탐색은1/10/15/20/25/30/35/40 각1회(기실행 제외). 최초 메모리 중단 수 이상은 추가 실행하지 않는다. 빠른 통과 설정의±4 정수(1~40)를 추가1회 검사한다. 서로 다른 설정 최대17개.
- 빠른3개와 전체 기준선(중복 제거)을 사전 동결해 추가3회씩 순환 확인. 매회완주·근거손실0·측정오류0·4GiB 미만·보호중단0인 조건의 확인 중앙값 최저를 선택한다. 이번에는 사용자의 최단 시간 목표를 따라5% 이내 작은 값 규칙을 사용하지 않는다.
- 후보와 기준선을 기존 동작8페이지/두 합성 탐색20초에서 각2회 확인한다. 실패 시 후보를 자동 승격하지 않고 미검증/실패 범위를 보고한다. 작은 자료/큐의 실제 최대 동시 수를 명시한다.
- 최대41실행/전체1시간, 고정 수집600초/프로세스630초, 탐색20초/프로세스60초. 완료 원본 비보관의 탐색/근거 보존을 기존 fixture에서 먼저 확인한다. 메모리 보호는 낮은 임계값의 실제 취소 시험으로 확인한다.
- 결과는 이 실험 입력/범위의 가장 빠른 확인 후보다. 전 사이트 전역 최적·순간 메모리 절대 보장·원래 수집되지 않던 클릭/늦은 댓글 해결·25분 HCX 운영 검증을 주장하지 않는다. 같은63페이지에 맞춘 선택 가능성과 중단 조건을 공개한다.
