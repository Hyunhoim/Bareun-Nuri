# AntiSpoof 토크나이저 정보 손실 진단

2026-09-30. 학습/API/모델추론 없이 현재 tokenizer와 기존개발 old624/role300/scope216 및 해당 표기에 등장하는155문자를 조사했다. 문자 단독/동일한 표기 마커 입력은 원인 진단이며 새 성능 평가가 아니다.

- 문자 단독155종 중41종이 UNK를 포함하고, U+코드포인트 표현은155종 모두 UNK가 없고 서로 다른 토큰열이었다.
- 문자 단독 충돌2그룹, typed 보조 근거 포함2그룹, 코드포인트 제거 압축6그룹이다.
- typed에서 NFD자모12종(초성·중성)과 전각영문5종(b,d,f,n,r)이 같은 토큰열에 들어갔다. 둘 다 confusables 직접대응이 없어 문자별 코드포인트가 보조 근거에 실리지 않는 경우다. 문맥까지 동일하면 결정적인 분류기는 이들을 서로 다르게 출력할 수 없다.
- 이는 UTS표가 모든 Unicode문자를 수록한 사전이 아니라는 점과 tokenizer의 미등록문자 처리가 결합한 입력 결함이다. 실제 원문에서는 구별 가능하지만 모델 입력에서 소실된다. 코드포인트 전부 제거는 이 구별 경로를 더 줄였다.
- 반면 기존개발1140개 전체입력에서 서로 다른 정답이 완전히 같은 토큰열인 충돌은 양쪽0이었다. 전체 문맥·다른 표기 정보가 남으므로 기존 모든 실패를 이 원인만으로 설명하거나 개선량을 예측하지 않는다.

## 제한된 인코딩 가설 확인

기존 typed 근거를 유지하고 직접대응표에 없는 비ASCII 문자만 원문 코드포인트/위치 목록으로 보충했을 때155문자 probe충돌은0그룹이었다. 그러나 저장44구간에서는512초과9→10,평균24.02토큰추가로 길이 문제가 더 나빠졌다. 정확도 실험/채택 근거가 아니며 운영에 연결하지 않았다.

## 다음 방향

단순 추가학습이나 코드포인트 삭제보다, **미등록 문자의 구별 가능성을 보존하는 입력 설계**가 필요하다. 동시에 이미 긴 입력을 더 길게 만드는 수정은 채택할 수 없다. 원문/문맥/위치는 별도 근거로 보존하면서 모델이 사용하는 문자 정보의 중복 표현을 줄이는 설계를 검토하되, 그 표현에 맞춘 학습과 기존 정탐·정상·보류·길이 검증을 함께 해야 한다. 코드포인트가 유용한 특징이라는 사실은 과적합 확정과 다르며, 같은 합성자료/개발집합 의존 위험은 계속 남는다.
