# 출력 형식 개선의 운영 배치 확인

`semantic-low-plan.md` 첫 응답에서 같은 문맥·분류 지침의 native structured 조건과 prompt JSON 조건이 다르게 판정했다. API 버그나 추론 효과로 단정하지 않는다. prompt JSON은 스키마가 시스템 문장에도 들어가므로 형식 전달·스키마 노출 방식이 함께 변한다.

후속 비교는 **새80개를 열기 전** 개발64개에서 다음을 고정한다.

- O: 원래 운영 joint 판정·native structured.
- J: 같은 joint+문맥 출처의 native structured 대조군. JJson과 형식 전달 차이를 분리한다.
- JJson: 이전 J(원래 joint 판정+문맥 출처)를 그대로 사용하고 prompt JSON만 적용. 기존 관찰 기법 출력 유지 가능성을 검증한다.
- passageJson: 간결한 게시 행위 분류·prompt JSON, 의미 전용.
- 모두16배치/none/온도0/seed42/출력3072. 최대16요청/450,000예약토큰/1시간, 공유48kTPM/최대2병렬.
- F1이 가장 높은 후보를 고르고 1%p 이내면 호출·토큰·지연·기존 출력 호환성을 함께 비교한다. 기법 정확도는 별도 보고한다. 최종후보를 고정한 뒤 새80개 정순·고정섞기 및 기존76개로 확인한다.
- 자유 JSON에서도 원래 로컬 검증은 유지한다. 설명 뒤에서 JSON만 억지 추출하거나 잘못된 판정을 코드로 정답에 맞게 바꾸지 않는다. 형식 실패는 조건 실패다.

## 실행 제어 보정 (점수 선별 전)

v1은 직전 low 실험의 토큰 창이 남아 JJson 첫 요청이 명시적429로 거절됐다. O/J 첫16개 응답2개는 보존한다. 61초 창을 지나 v2에서 완전히 같은 요청 body임을 확인한 두 응답을 재사용하고 남은 배치만 실행한다. 미확인 요청은 없다. 두 실행 합계16성공+429거절1=최대17시도로 실행 예산만 보정하고, 후보/프롬프트/입력/채택 기준은 그대로다. 실행 간 마지막 요청 시각을 보존해 동일 문제가 반복되지 않게 한다.
