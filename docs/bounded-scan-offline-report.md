# 디스크 근거 저장·제한된 활성 페이지의 오프라인 검증

2026-09-25. 운영 코드는 바꾸지 않았다. 아래 실행은 저장된 수집 자료와 정상 고정 Mock 판정만 사용했으며 API 호출·브라우저 실행은 0회다. 따라서 광고 판정 F1이나 실제 25분 운영 성능 검증이 아니다.

## 구현 범위

`agent/experiments/bounded-scan-store.cjs`는 원본 페이지 snapshot과 배치별 판정을 각각 SHA-256으로 확인하는 파일에 원자 저장한다. 체크포인트에는 페이지 파일 참조, 진행 offset, 판정 파일 참조, FIFO frontier, 요청 상태를 둔다. 원문·문맥·스타일·좌표·iframe 근거는 삭제하거나 요약하지 않는다. 장문 분할·결과 통합·관찰 기법 통합은 운영 함수를 재사용한다.

`bounded-scan.cjs`는 FIFO 방문 순서를 유지한다. 미완료 페이지의 논리적 창은 2개 또는 8개이고, 원본 근거 캐시는 최대 2페이지다. 수집 전 기존 캐시를 1개로 줄여 새 수집 자료의 자리를 확보한다. 페이지별 판정은 기존 순서대로 최대 4개, 동시성은 1이다. 새 페이지 하나를 입장시킨 뒤 판정하는 RR은 **새 페이지 입장 우선 + 활성 대기열 순환**이다. SRPT8은 남은 4개 배치 수가 적은 페이지를 우선하되, 마지막 처리 후 8턴 이상 기다린 페이지가 있으면 가장 오래 기다린 페이지를 먼저 처리한다. 광고 라벨이나 특정 페이지 예외는 사용하지 않는다.

활성 창이 찬 동안 새 페이지를 무제한 수집하지 않는다. 완료 페이지의 근거 캐시는 해제한다. 미확인 전송은 자동 재개하지 않으며, 전송 전 취소와 전송 후 불명 상태를 구분한다. 전체 자료를 복원하는 `materialize`는 감사 전용이고 실행 루프에서는 사용하지 않는다.

## 큰 대기열: 같은 300회 Mock 호출

자료는 `.runtime/throughput-e2e-mock-v1/snapshots`의 실제 수집 snapshot 21페이지·4,307후보다. 기록은 `.runtime/bounded-backlog-replay-v1`에 있다. 모두 호출 상한으로 부분 종료했다.

| 조건 | 수집 페이지 | 판정 work | 체크포인트 누적 쓰기 바이트 | 최종 체크포인트 바이트 | 표본 최대 RSS 바이트 | 벽시계 초 |
|---|---:|---:|---:|---:|---:|---:|

체크포인트 반복 직렬화·쓰기 감소는 직접 확인됐다. 그러나 표본 RSS는 대안에서 더 높았다. **근거 캐시 2페이지 제한을 전체 메모리 개선으로 표현하면 안 된다.** 파싱·직렬화의 임시 할당, GC, 출력 결합과 frontier 메타데이터는 남아 있다. 메모리 보호 상한도 계속 필요하다.

벽시계는 기준선 일부가 별도 API 실험 및 QA와, 후보 실행 일부가 사이트 QA와 겹쳤다. 같은 장비에서의 통제된 속도 배수나 실제 HCX 지연 개선으로 해석하지 않는다. 재현 가능한 쓰기 바이트와 처리 집합을 우선 근거로 사용한다. replay의 `atomic_bytes_written`은 계측된 원자 파일 쓰기이며 스트리밍 `writeSync` 전체를 포함하는 총 디스크 I/O가 아니다.

부모의 별도 정답 위치 감사에서는 RR8이 광고 28개 중 15개를 수집하고 6개를 판정 입력까지 전달했으며, SRPT8은 19개/8개였다. 기존 조건은 광고 수집 0개였다. 이는 이미 관찰한 개발 자료의 처리 위치 수치이며 Mock 판정의 탐지 성능이 아니다. 관련 원본은 `rr8-reach-audit.json`, `srpt8-reach-audit.json`이다.

## 유한 그래프 전체 보존

`.runtime/semantic-worker-replay-production-v1/source.json`의 81페이지·615후보/관찰 자료를 사용한 `.runtime/bounded-finite-replay-v1`에서는 기준선과 세 대안 모두 전체를 완료했다. `parity-audit.json`에서 페이지, 후보, work, 기법 관찰, 운영 `combine` 결과의 전체 집합 일치를 확인했다.

기준선은 154배치, 세 대안은 각각 201배치였다. 페이지 끝의 잔여 후보를 다음 페이지와 묶지 않아서 **호출 수가 30.5% 증가할 수 있는 비용**이 확인됐다. API 입력을 실제로 보내지 않았으므로 의미 판정과 토큰 비용 차이는 별도 검증 사항이다. 이 초기 유한 재생 뒤 캐시와 진단 표시 문구를 보완했으므로 당시 archive와 최종 소스 SHA가 다르며 당시 원본 측정은 보존했다.

## 재개·예외 검증

최종 `.runtime/bounded-scan-test-1790321804733/result.json`은 drain1, RR2, RR8, SRPT8, 4배치 quantum의 5조건을 통과했다. 10페이지·102개 합성 후보와 장문 분할을 사용했다.

- 전체 원문·관찰 보존, 페이지 내부 순서, 중복 판정 없음, 캐시 최대 2페이지.
- 각 조건의 3호출 중단/재개와 무중단 실행의 정확한 배치 이력 일치.
- 준비 상태의 deadline 취소는 재개 가능, 전송 후 미확인은 자동 재개 거부.
- 사용자 취소의 대기 URL 보존, 근거 파일 변조 시 checksum 거부.
- 체크포인트에 전체 후보·전체 판정 배열이 없음을 확인.
- 8턴 aging의 오래 기다린 페이지 처리 및 마지막 호출 상한과 정확히 동시에 끝난 경우 `completed` 처리.

마지막 완료 경계 보정은 위 테스트에서 확인했다. 앞의 300호출 비교는 모두 미완료 상태라 그 경계 보정의 영향을 받지 않는다. 실제 저장 snapshot의 전체 보존과 합성 자료의 정확한 재개는 확인했지만, 별도의 실제 21페이지 snapshot 중간 재개 재생은 아직 수행하지 않았다.

후속 caller 대조에서 `frontend/src/App.tsx`가 `coverage.unjudged`를 직접 렌더링하고 재개 가능성에도 사용함을 확인했다. 경량 `index.work_locations`를 추가해 매 publish 때 원문 snapshot을 다시 읽지 않고 `coverage.unjudged`를 스트리밍한다. `run.json`의 기존 pending 배열, excluded, inflight, visited, call_records, technique_reviews도 유지한다. 두 diagnostics 파일은 배열이며 `result.meta`는 운영 `outputResult`를 사용한다. 저장 형식은 v2로 구분해 이전 location index 없는 체크포인트의 자동 재개를 막았다.

`.runtime/bounded-schema-1790322233297/result.json`은 실제 core와 새 runner를 각각 한 페이지·한 번의 4개 Mock 판정으로 비교했다. 기존 coverage/run 필드·타입, 남은 17개 위치, result meta 키·버전, diagnostic 배열, 실제 판정 입력 순서와 원본 후보의 동일성을 통과했다. 0.74초의 API0/브라우저0 검사이며 다른 유료 실행과 겹치므로 시간 지표로 쓰지 않는다. 이 출력 호환 수정 뒤 5정책 전체 재생을 다시 하지는 않았다. 앞의 300호출 쓰기량은 location index/coverage 보강 이전 측정값이고 최종 코드의 쓰기량 측정으로 대체하지 않는다. 운영 worker의 전체 후보 배열 의존 progress와 페이지 readiness 접근은 별도 어댑터가 필요한 상태다.

추가 양성·검토·장문 혼합 검사에서 diagnostics의 내용은 같지만 페이지별 결합 때문에 배열 순서가 달라짐을 발견했다. 기존 core 순서인 전체 의미 진단 → 관찰 전용 진단을 두 번의 파일 스트리밍으로 유지하도록 출력만 보정했다. 최종 `.runtime/bounded-results-1790322527251/result.json`은 3페이지·12후보·16work에서 findings 6개, diagnostics 6개, 관찰 진단 4개의 **내용과 순서**가 core와 정확히 일치했다. 원문·위치·기법, 전역 finding ID, 장문 양성/검토 통합, 미완료 장문 조기 출력 방지, 중단/재개의 정확한 요청 배치와 기존 판정 보존도 통과했다. `.runtime/bounded-schema-1790322529172`에서 출력 스키마도 재확인했다. 두 검사는 각각 약 1.44/0.91초의 Mock 검사이며 API·브라우저는 0회다. 알고리즘·모델 입력은 바꾸지 않았다.

## 남은 제한

매 배치마다 각 페이지의 결과 파일을 읽어 전체 출력 파일을 다시 만든다. 선택한 페이지의 이미 완료된 판정도 다시 결합한다. 체크포인트 비용을 줄였지만 이 출력 I/O·CPU 비용까지 제거한 구조는 아니다. 메타데이터와 결과 파일은 누적되며 디스크 용량 제한/정리 정책은 구현하지 않았다. 저장 실패 시 성공으로 처리하지 않지만, 디스크 고갈 해결을 검증하지 않았다.

SRPT는 남은 후보 수가 작은 페이지를 우선하므로 큰 페이지 뒤쪽 광고가 늦어질 수 있다. Aging은 이미 활성 창에 들어온 페이지의 기아를 제한하며, 미발견 URL이나 창 밖 페이지에 도달을 보장하지 않는다. RR8/SRPT8의 실제 광고 판정, 긴 페이지 앞·중간·뒤 위치의 손익, 새로운 자료, 25분 종단 성능을 확인하기 전 운영 채택을 주장하지 않는다.
