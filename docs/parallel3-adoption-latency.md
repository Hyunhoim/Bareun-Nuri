# 동시 3요청 운영 채택 및 지연 진단

2026-10-01 사용자 지시로 검증된 동시 3요청 구조를 운영에 반영했다. 의미 프롬프트·12후보 묶음·512출력·58k TPM·1초 발송 간격·FIFO·수집5·AntiSpoof 모델은 유지한다. 기법 모델은 직렬 호출하여 단일 프로세스 계약을 보존한다. Mock과 직접 사용하는 기존 순차 실험 경로는 judgmentConcurrency=1로 유지한다.

## 변경 및 검증

- `agent/src/core/bounded-scan.cjs`: 요청별 AsyncLocalStorage 귀속, 최대3개 예약, 완료 결과 영속 저장, 순서대로 커밋. 부분 응답의 실제 요청 번호 귀속 유지.
- `agent/src/worker.cjs`: HCX만 동시3 활성화, 공유 API 예산과 직렬 AntiSpoof 적용.
- `backend/src/main/java/kr/publicad/Jobs.java`: prepared/rejected/durable만 남은 wave 재개 허용. sent/responded가 남으면 거부한다. 저장 근거·체크섬·서명은 worker에서 검증한다.
- 실행 서명 변경으로 기존 순차 및 실험 체크포인트 자동 이행 없음. 백업 `.runtime/parallel3-adoption-1790792620069`.
- `local-benchmark/parallel3-operating-check.cjs`: 역순 응답 완료에도 순차와 배치·판정 일치, 부분 응답 귀속, durable 재개 시 추가 API0, 미확인·서명 변경 거부 통과. 재개는 상태 주입 검사이며 OS 강제 종료 시험은 아니다.
- `agent/experiments/bounded-worker.test.cjs --backend`: 실제 worker의 네트워크 stub에서 동시3·36후보 처리 확인, Spring Boot 재개 허용·거부와 기존 결과 보존 통과. `.runtime/bounded-worker-check-1790792843000`.
- 스키마·예산·응답 포장·짧은 마감 검사 통과. 백엔드 빌드 통과. 추가 유료 API0, 학습0, Phase2 미사용. 운영 승격 뒤 새25분 측정을 반복하지 않았고 채택 근거는 직전 실제25분 실험이다.

직전 실험의 정탐3손실·동일위치새오탐3은 미해결이다. 사용자 지정 채택이며 정확도 완전 보존 관문을 통과한 것으로 소급하지 않는다.

## 개선 우선순위

1. **느린 요청 때문에 완료 결과가 대기하는 문제.** 마지막 한 요청69.169초 때문에 약4.9초에 끝난 두 요청의24후보도 마감 전 반영되지 못했다. 완료 결과를 독립적으로 반영하면 유효할 가능성이 가장 명확하다. 페이지별 접두 처리·체크포인트·재개·후보 순서 보존을 검증한 뒤 별도 채택한다. 이번 승격은 측정된 묶음 방식 그대로이며 이 변경까지 섞지 않았다.
2. **매 이벤트의 전체 상태·결과 재출력.** 체크포인트404,985,343bytes, 결과출력295,069,880bytes, 저장소읽기107,365회. `account/persist`가 요청 상태마다 누적 call_records를 복사·저장하고, `progress/publish`가 완료 페이지 출력을 반복 읽고 재작성한다. 작업 증가에 따라 부담이 커질 구조다. 다만 저장시간은 별도 측정되지 않았으므로 168초 전부를 저장 병목으로 주장하지 않는다. 우선 시간을 계측하고, 안전한 요청 장부는 그대로 두되 사용자용 결과 전체 재출력 주기만 줄이는 방식을 검증할 가치가 있다.
3. **기법 CPU 및 후처리 시간 분리 계측.** AntiSpoof는 단일 CPU 프로세스로 순차 처리한다. 기존 로그에 독립 소요 시간이 없어 현재 주병목이라고 확정할 수 없다. 광고 양성 수 증가에 비례하는지, 모델 초기화와 정상 추론 중 어느 구간인지부터 확인해야 한다.
4. **페이지 안정화 대기.** 95페이지의 준비대기 합102.03초, 탐색11.94초, 추출13.97초다. 페이지들이 겹쳐 수집되므로 합산 수치를 절감 가능 경과시간으로 보지 않는다. 동적 댓글·스타일·iframe 근거를 보존하는 조건부 종료만 검토한다.
5. **입력 토큰과 예약 대기.** 전체 요청 입력1,004,373·출력93,090토큰. 출력보다 입력 부담이 크지만 정상 후보 제외나 문맥 삭제는 이전 회귀 위험이 있다. 정확히 중복된 표현의 손실 없는 정리가 후보이며, 현재 로그의 전용 발송 대기50초만으로 한도 확대를 우선할 근거는 부족하다.

API 요청당 지연이 가장 긴 측정 구간이지만 입력 축약이 의미 정확도를 유지할지는 별도 문제다. 가장 먼저 검증할 구현 개선은 완료 결과 대기 해소이며, 뒤이어 저장·CPU의 분리 계측을 권한다. 남은 병목을 이번에 해결했다고 주장하지 않는다.
