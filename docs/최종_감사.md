# 바른누리 제출 폴더 최종 감사

감사일: 2026년 10월 8일
대상: `Bareun-Nuri 제출`
대조 자료: 「공공 웹사이트 불법광고 탐지 도구 개발 공모전 모집요강」 원본 PDF·HWPX

## 감사 결론

제출 폴더의 불필요한 개발 문서와 이전 실행 기록을 정리하고, 사용설명서와 소스 README를 현재 Luna 운영 구조에 맞춰 수정했다. 실제 실행 점검에서 발견한 CPU Python 의존성 접근 오류도 복구했다. 포함된 실행기, 브라우저 수집, CPU 모델 추론, 백엔드·사용자 화면과 소스 재빌드가 이번 장비에서 동작했다.

파일 구성과 출력 계약은 확인한 요강에 부합한다. 다만 주최측이 사용할 별도 Windows PC와 API 키는 이번 감사에서 사용하지 않았다. 실제 심사 환경의 실행·성능과 평가 통과까지 보장하는 결론은 아니다. 광고 정확도를 다시 측정하거나 운영 판정 설정을 변경하지 않았으며, 외부 모델 API 호출은 0회다.

## 1. 제출 폴더와 불필요한 파일

제출 폴더 밖으로 보관한 항목은 다음과 같다. 신청 서류는 수정하지 않았다.

- 오래된 Agent·백엔드·프론트엔드 README 3개: 소스 최상위 README 하나로 통합했다.
- 제출본에 없는 개발 자료를 참조하던 모델 포장 도구, 실험 파일, 이전 검증 스크립트: 실행·재빌드에 필요한 파일만 남겼다.
- 개발 장비의 백엔드 로그와 실행기 상태·잠금 기록: 제거하고 검사 이력은 비어 있는 상태로 정리했다.
- JAR에 누적된 이전 화면 파일 40개: 재빌드본으로 교체했다. 현재 사용하는 화면 파일과 Java 클래스 17개의 내용은 교체 전후 동일했다. 이후 빌드는 `clean package`로 이전 산출물이 남지 않도록 했다.

제출 소스에 없던 실행기 아이콘 파일을 추가해 C# 재컴파일에 필요한 입력을 갖췄다. 제외한 시험 파일을 호출하던 `package.json`의 명령도 정리했다. 현재 소스에는 API 비용 없이 실행할 수 있는 제출 검증 스크립트 하나를 제공한다.

LICENSE·NOTICE·모델 출처·폰트 및 외부 구성요소 고지는 남겼다. 이들은 불필요한 개발 문서가 아니라 배포에 필요한 출처·이용 조건 자료다. 동일 모델 가중치는 실행 폴더에 한 벌만 두고, 소스 재실행 시 이를 복사하도록 안내했다.

```text
Bareun-Nuri 제출/
├─ 사용설명서.md
├─ 01_실행/       실행기·백엔드·Agent·모델·포함 런타임·외부 설정
├─ 02_소스코드/   README 하나·프론트·백엔드·Agent·빌드/검증 도구·고지
└─ 03_신청서류/   참가신청서·서약서·동의서·기획서
```

감사 보고서와 파일 목록, 백업, 시험 로그는 제출 폴더 밖에 보관했다. 실행에 필요하지 않은 개발 데이터셋과 실험 보고서는 제출 폴더에 추가하지 않았다.

최종 폴더는 **22,280개 파일·2,446,345,035바이트(약 2.28 GiB)**다. 전체 파일을 실제로 읽어 SHA-256 목록을 만들었으며 접근 오류는 없었다. 프로젝트 작성 문서는 최상위 사용설명서와 소스 README만 남았다. 검사 이력·로그는 0개, 외부 설정의 키는 빈 값이다. Agent·기법 추론·백엔드·화면 소스 41개 파일을 개발본과 대조해 내용 일치를 확인했다. 키 형식 검색에서도 발견된 키는 없었으나, 패턴 검색 자체를 완전한 보안 감사로 해석하지 않는다.

## 3. 사용설명서와 README 수정

사용설명서는 결과 파일 위치를 가장 먼저 배치하고, 실행 → 키 등록 → 검사·중지·재개 → 결과·이력 → 문제 해결 순서로 정리했다. 이전 HCX 실험 수치와 오래된 개발 안내를 삭제하고 현재 `OpenAI Responses API / gpt-6-luna / OPENAI_API_KEY`를 적었다.

사용자 일시 중지는 남은 시간을, 시간 초과 재개는 새 25분을 사용하는 차이를 표로 설명했다. 검사 시간 막대·후보 판정 완료율이 사이트 전체 검사율을 뜻하지 않는다는 점, 부분 결과와 미판정의 의미도 간단히 안내했다. JSON 필드와 원본·첫 구간 결과 위치, 로그 위치를 함께 제공한다.

소스 README는 한 개로 통합했다. 담당자가 일반 실행과 소스 재빌드를 구분할 수 있도록 안내하고, 현재 모델·운영 설정·소스 위치·빌드 명령·포함 CPU 모델 재사용·API 비용 없는 검증 명령을 적었다. 제외된 실험 자료나 이전 저장소 브랜치를 요구하던 안내는 제거했다.

## 4. 실제 실행에서 발견한 문제와 확인 결과

### CPU Python 의존성 접근 오류

제출 Python에서 PyTorch 폴더 등 5개 디렉터리에 접근할 수 없어, `torch` 버전이 읽히지 않고 Transformers 초기화가 실패했다. EXE가 웹 화면을 열더라도 기법 모델은 시작되지 않을 수 있는 문제였다.

기존 의존성 폴더는 백업하고 읽을 수 있는 의존성을 새 폴더에 옮겼다. 접근되지 않던 PyTorch 구성요소는 공식 CPU 저장소의 **동일 버전 `2.6.0+cpu`** 휠로 복구했다. 모델 가중치·토크나이저·판정 설정은 변경하지 않았다. 복구 뒤 포함 Python과 실제 AntiSpoof 추론을 실행해 정상 응답을 확인했다.

## 5. 제출 시 남아 있는 확인 사항

- 별도 Windows 11 x64 PC에서는 이번에 직접 실행하지 않았다. 현재 장비의 개발 도구가 설치되어 있지 않아도 실행되는지 새 PC에서 확인하면 배포 근거가 더 강해진다.
- 주최측 API 키의 모델 접근 권한·잔액·요청량 한도·네트워크 조건은 확인하지 않았다. 설명서에는 필요한 서비스와 설정을 명시했다.
- 서류 날짜는 10월 9일로 작성되어 있다. 실제 제출일을 다르게 정한다면 서류 날짜를 최종 확인한다. 신청자 서명·날인의 효력이나 참가 자격을 기술 검사로 보증하지 않는다.
- 포함 런타임과 모델 때문에 제출물 용량이 크다. 요강의 이메일 접수 주소와 마감 시각을 따르되, 실제로 전달할 수 있는 대용량 전송 방법을 확인한다.

제출 폴더 밖의 `.runtime/final-submission-audit-2026-10-08`에 제거 항목 목록, CPU 복구 영수증, 실행기 점검 결과, 재빌드 비교와 최종 파일 목록·SHA-256을 보관했다. 감사 중 GitHub push나 서류 발송은 하지 않았다.
