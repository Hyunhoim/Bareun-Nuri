# 처리량 병목: 예약기 독립 진단

2026-09-26. 운영 변경·유료 API 0회. 자료: `.runtime/scale-large-live-v1`의 실제 467개 요청·응답.

## 가설과 고정 조건

현재 순차 요청은 로컬 52,000 TPM 예약, 61초 창, 최소 간격 1초, 매 1초 대기 재확인을 사용한다. 수집·저장 간격과 요청 본문·서비스 시간·순서를 그대로 두고 다음 가설을 분리 계산했다.

- 불필요한 1초 재확인 지연을 정확한 다음 허용 시각으로 줄이면 큰 이득이 있는가?
- 61초 안전 창의 1초 여유가 주요 병목인가?
- 당시 실제 한도 60,000보다 낮은 52,000 예산의 여유가 큰가?
- 요청 전 보수적인 문자 기반 토큰 추정이 병목인가? 마지막 항목은 사후 실측 prompt 토큰을 미리 아는 가상 상한이며 실행 가능한 개선으로 취급하지 않는다.

최종 채택 실험이 아닌 오프라인 진단이다. 실제 지연 감소·새 F1을 주장하지 않는다. 응답 시간을 바꾸거나 남은 432개 요청을 외삽하지 않는다.

## 관측 근거

467개 모두 HTTP 200이며 응답 헤더의 `x-ratelimit-limit-tokens=60000`, `x-ratelimit-limit-requests=60`이 일치한다. 남은 토큰 최저 8,794, 남은 요청 최저 32였다. 이는 당시 계정/엔드포인트 관측이며 현재 계정 한도나 다른 모델의 한도를 보장하지 않는다. 새 API 요청은 하지 않았다.

실제 응답 서비스 합 936.181초, 예약 대기 합 466.372초다. 요청 전 추정량은 각 응답 뒤 사용하는 `prompt_tokens + 512`보다 최소1.268배·평균1.467배·최대2.372배 컸다. 실제 생성 토큰으로 512 예약을 환급하는 안은 검토하지 않았다. 첫 응답 헤더의 차감량도 prompt1,121+출력상한512=1,633과 일치한다.

58k 재생의 모든 60초 구간을 별도 검사하면 `prompt+512` 최대56,900토큰, 최대30요청이다. 이 저장 요청 집합에서는 당시 응답 헤더 한도 이내지만 실서버의 정확한 창 구현·다른 동시 사용자 트래픽은 재현하지 않았다.

## 후속 권고

**하나를 고르면 58,000 TPM 예약 단독 비교가 가장 현실적이다.** 61초 창, 1초 최소 간격·재확인, 기존 보수적 추정·출력512·순차4개를 유지하면 변경 요인이 하나다. 새 실제 비교의 첫 응답에서 최소60k/60RPM을 재확인한 뒤에만 58k로 진행하며, 확인 전에는52k를 유지한다. 명시적429 또는 예상치 못한 한도 축소가 관측되면 중단하고 자동 재시도하지 않는다. 다른 유료 실험과 동시 실행하면 공유 할당량 간섭으로 효과를 구분할 수 없으므로 같은 계정 비교는 순차 실행해야 한다.

정밀 타이머 단독은 예상0.58%로 이번 우선순위가 낮다. 사후 oracle 결과만 보고 추정치를 임의로1.467로 나누는 보정은 권하지 않는다. 같은 한국어/문서 집합에 맞춘 토큰 추정 과적합 가능성이 있고 다른 문구·형식에서 과소 예약할 수 있다. 정확 토큰 계산 API를 매번 추가 호출하는 변경도 그 비용·지연을 포함한 별도 가설이다.

운영 채택 전에는 같은25분에서 실제 처리량·전체 광고기준F1·기존TP 손실·FP·429·미확인 요청·비용과 재개 보존을 검증해야 한다. 입력/출력 계약이 같아도 모델의 반복 변동과 새로 판정되는 영역의 오탐을 확인해야 한다. 이 진단만으로 운영을 상향하지 않았다.

재현: `node .runtime/throughput-quota-v1/replay.cjs`. 모든 요청 본문의 SHA256, 저장예약량과 추정함수 일치, 출력상한512, HTTP 상태, 한도 헤더, 60초 토큰/RPM, 기준선 재생 오차, 최소 간격 제거 무효를 assert로 검사한다. 결과는 같은 폴더의 `summary.json`, `rows.json`, 각 조건 JSON에 저장한다.

## 추가 검토: 현재 C의 배치8 단독 가설

과거 배치 확대 실패가 현재 C/512/배치8의 검증은 아니다. `docs/semantic-reference-plan.md`의 reference8은 evidence_ids 선택을 추가하는 옛 출력 계약이다. `replica-intent-round2.cjs`의 role8은 준비돼 있으나 실제 기본 실행 모드는 role4/role16/reading4/nominal4이며 보고서에 role8 실측은 없다. role16은 역할 지시와 target_element/context_roles가 추가된 계약, 출력1024, 자동 자모 복원C 적용 전이다. `docs/replica-intent-report.md`가 이 차이를 명시한다.

따라서 **현재 C의 입력/분류/출력512를 유지한 배치4→8만의 비교는 독립된 유망 가설**이다. 호출별 고정 지시와 출력 예약의 반복 부담을 줄일 수 있다. 저장467요청의 고정 system 접두부는657문자다. 모든 요청을 절반234개로 합칠 수 있다는 이상 조건이면 이 접두부153,081문자와 출력 예약119,296토큰이 줄어든다. 문자수는 토큰수가 아니며 페이지경계·입력크기 때문에 실제 요청을 절반으로 합치지 못할 수 있다. 이를 종단속도 예측으로 사용하지 않는다.

과거 role16의 인용 오탐/광고 누락과 배치 구성 변동은 경고 근거다. 같은 후보 두 순서에서 현재C와 B8을 직접 비교하고 기존TP·FP·보류·출력잘림을 확인해야 한다. 과거 role16 출력374~387토큰 관측은 B8/512 실험의 참고이지, 현재 계약의 출력상한 안전성 보증이 아니다. 출력오류를 잘라 복구하거나 상한을 늘려 배치단독실험을 바꾸지 않는다. API0 검토만 수행했다.
