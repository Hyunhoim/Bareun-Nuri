# 0~1단계 구현 및 검증 (2026-09-22)

목표는 특정 문구를 맞추는 수정이 아니라 수집 실패의 공통 원인을 줄이는 것이다. 합의한 0~5단계 순서는 루트 AGENTS.md에 기록했다. 이번 구현 범위는 0~1단계다.

## 구현

- 0단계: React 기본값·입력 상한, Spring 요청 검증, Node 실행 검증의 제한 시간을 3600초로 통일했다. 실제 경과 시간과 `exceeded30Minutes`를 기록한다. 페이지 200개·후보 10000개·호출 300회 한도는 유지한다. 제한 초과는 실패로 남기고 완료 결과를 만들지 않는다.
- 1단계: 첫 article/main만 선택하던 범위를 document.body 전체로 확대했다. 댓글·답글·작성자·서명·하단 문구도 DOM 구조로 탐색한다. 광고 어휘나 라벨·사례 ID를 수집 조건으로 사용하지 않는다.
- 연속 인라인 조각은 소유 텍스트 요소로 합친다. blockquote/strong/custom element 등을 고정 허용 태그 목록 때문에 버리지 않는다. 링크와 시각적 숨김 상태가 다른 자식은 별도 위치를 보존한다. flex/grid의 독립 항목은 합치지 않는다.
- 원문 문자와 CSS 위치·iframe 경로·스타일 근거를 보존한다. script/style/template/noscript/iframe 내부의 비본문 데이터는 텍스트에서 제외한다. iframe 문서는 따로 수집한다.
- 고정 300ms 대기 대신 최소 1000ms 관찰, DOM 변화 후 300ms 정지, 진행 중인 document/fetch/xhr 요청과 aria-busy, 하위 프레임 준비 상태를 확인한다. 관찰 상한 5000ms에서 안정화 미확인은 경고로 남긴다.

LLM 프롬프트·정규화·광고 판정·관찰 신호 규칙·배치 16·직렬 실행은 유지했다. 문맥 귀속(2), 의도와 기법 계약(3), 판정 재사용/병렬화(4), 페이지 우선순위(5)는 변경하지 않았다.

## 실제 HCX 비교

기존 페이지 목록에서 0번부터 매 9번째 페이지를 골랐으며 정답·문구를 보고 선택하지 않았다. 선택한 10개 페이지의 모든 후보를 두 버전에서 각각 판정했다. 이전 저장 결과의 판정만 재사용하지 않고 양쪽을 다시 호출했다.

HCX-007, temperature 0, reasoning none, seed 42, maxTokens 3072, 배치 16, 직렬 호출을 동일하게 유지한다. 후보 집합 변화로 배치 구성은 달라진다. 비교 시간은 수집이 제외된 판정 시간이다. 전체 300개 정확도 측정으로 확대 해석하지 않는다.

## 해석과 남은 범위

- 누락의 공통 원인인 수집 범위·태그 제한·인라인 분절·짧은 대기 문제를 개선했다. 기존 오류를 분석한 세트 재검사이므로 일반화 성능 향상 확정이나 새 홀드아웃 점수로 보고하지 않는다.
- 문서 전체를 수집하면서 반복 메뉴·접근성 문구 등이 늘어 후보 수가 약 2배가 됐다. 1시간 제한 확대만으로 전체 처리가 보장되지 않는다. 실제 지연·호출·토큰 증가를 함께 평가해야 한다.
- 현재 단위는 DOM 텍스트 요소다. 임의의 긴 요소를 자연어 문장마다 별도 CSS 위치로 나누는 기능은 없다. 직접 텍스트와 중첩 요소가 섞인 경우 부모/자식 후보가 겹칠 수 있다.
- 로딩 안정화는 관찰 구간의 상태다. 표시 없는 늦은 타이머·클릭 뒤 콘텐츠·무한 스크롤·Shadow DOM·CSS 생성 콘텐츠까지 보장하지 않는다.
- 다음 작업은 합의한 2단계 문맥의 범위와 귀속 개선이다. 반복 메뉴 제거를 먼저 강하게 적용하면 탐지 대상도 버릴 수 있어 이번 단계에서는 후보 제외 규칙을 추가하지 않았다.
