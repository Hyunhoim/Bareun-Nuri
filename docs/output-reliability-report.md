# HCX 출력 신뢰성 비교 결과

2026-09-30. 결론: **Structured Outputs는 이번 설정에서 미채택, 불완전 응답 격리는 안전성 연구 검증 통과이나 운영 채택 보류. 현재 운영 소스는 유지했다.**

## 1. Structured Outputs 실호출 비교

사전 계획 `output-reliability-plan.md`에 따라 기존 Phase1의 정상 완료 159묶음에서 ID 해시순으로 18묶음을 선택했다. 서로 다른 후보184개 중 지정 정답 위치82개(광고46/정상36)에서 의미 성능을 평가했다. 나머지102개는 미라벨이므로 정상으로 간주하지 않았다. 소비된 합성 Phase1의 회귀 진단이며 독립 평가나 사이트 전체 F1이 아니다.

A=현재 prompt JSON, B=공식 responseFormat JSON schema. A-B-B-A 순서로 각각18호출, 총72호출했다. 동일 후보/순서/사용자 입력/기본 의미 지시/HCX-007/none/온도0/seed42/출력512를 확인했다. 스키마의 전달 위치는 의도적으로 다르다. B는 system에 붙이던 스키마를 API responseFormat으로 전달한다. 공식 근거: https://api.ncloud-docs.com/docs/clovastudio-chatcompletionsv3-so

반복별 A F1은85.19/85.98%, B는82.57/82.57%다. A대비 B는 각 회차 기존 정탐1개를 잃었고 새 오탐2/3개가 생겼다. 전체184후보의 이진 판정 변화는 회차별4/5개다. A자체 반복은 이진1개·4분류1개, B는 이진0개·4분류1개가 달랐다. B의 반복 안정성만으로 정확도 우위를 주장할 수 없다.

B의 F1은3.01%p 하락했고 요청 중앙 서비스 시간은22.59%, 18묶음 평균 실행시간은22.31% 증가했다. 입력 토큰은 다소 줄었으나 출력 토큰은14.96% 늘었다. 대기 합계는 각 회차0.003~0.007초여서 이번 지연 차이는 로컬 TPM 대기 증가로 설명되지 않는다. 다만 단일 시간대·18묶음의 관측이며 출력 길이만이 원인이라고 단정하지 않는다.

**사전 확대 기준 중 F1 하락1%p 이내·새FP1개 이하·중앙지연20% 이내를 통과하지 못해 추가25분 유료 비교를 하지 않았다.** 두 방식 모두36회에서 오류가 없었으므로 희귀 ID 누락 감소 효과도 아직 입증되지 않았다. Structured Outputs 자체가 항상 나쁘다는 결론이 아니라, 현재 요청 계약으로의 단순 전환을 채택할 근거가 없다는 뜻이다.

## 2. 불완전 응답 격리 검증

운영 모듈을 수정하지 않고 연구 실행 경로에서만 적용했다. HTTP200·정상 종료·완전 JSON·요청 ID의 유효한 일부만 반환한 경우에 한정했다. 응답 원문과 반환된 판정은 격리 파일에 보존하고, 누락 후보에 정상 판정을 채우지 않는다. 전송 여부 불명, 잘림, 중복키, 알 수 없는 ID, 잘못된 분류 값은 기존처럼 실패 처리한다.

실제 Phase1의160번째 저장 응답에서11개 반환/1개 누락을 오프라인 확인했다. 이 실패 요청은 다시 보내지 않았고 원래 체크포인트도 변경하지 않았다.

API를 호출하지 않는 실제 세션·체크포인트 경로 검증에서 다음을 확인했다.

- 오류 뒤 다른 페이지 검사를 계속한다.
- 기존 정상 완료 조건의 판정은 변경 전과 완전히 같다.
- 빠진 판정은 coverage의 미판정으로 남고 완료로 표시되지 않는다.
- 호출 예산으로 중단한 뒤 재개해도 격리 요청을 자동 재전송하지 않는다.
- 비정상6조건(알 수 없는 ID/잘못된 값/중복/깨진 JSON/길이 종료/통신 오류)은 격리로 우회하지 않는다. 해당 미확인 요청의 재개도 새 호출 없이 거부한다.

**중요한 한계:** 최소 연구 구현은 오류가 난 요청만이 아니라 해당 페이지의 남은 판정을 모두 보류한다. 12후보 오프라인 시나리오에서는10판정/2미판정이 됐다. 실제 실패 시점의 페이지는 offset24/총39후보여서 이 방식을 적용하면 빠진1개 외에도 총15개가 미판정으로 남는다. 유효하게 반환된11개도 격리 근거로만 저장하고 결과에 부분 커밋하지 않는다. 안전하지만 검사 손실이 커질 수 있다. 격리 페이지를 사용자가 명시적으로 다시 검사하는 기능과 UI는 구현하지 않았다.

원자료 `.runtime/incomplete-response-1790737379121/result.json`, 실행 `local-benchmark/incomplete-response-check.cjs`, 연구 구현 `incomplete-response-candidate.cjs`. 이 검증은 stub 응답을 사용한 제어 흐름·저장/재개 검사이며 실제25분 처리량이나 F1 개선 증명이 아니다.

## 채택 판단

1. **Structured Outputs: 미채택.** 이번 설정에서 의미 성능과 지연 모두 악화되어 현재 방식을 유지한다.
2. **응답 격리: 후속 후보로 보존, 현재 구현은 운영 미채택.** 전체 작업 중단을 피하는 효과는 검증했지만 페이지 단위 보류의 손실과 명시적 재처리 계약이 남아 있다. 다음에는 미완료 요청 범위만 따로 보존하고 같은 페이지의 다음 묶음도 처리하는 계약을 검증하는 편이 낫다. 정상 채우기/자동 재호출은 금지한다. 이후 동일25분 조건에서 전체 정탐 수·미판정·재개 보존을 확인해야 한다.

이번에는 학습·의미 프롬프트 수정·운영 변경·원래 실패 요청 재호출·push를 하지 않았다. 새 과적합 조정 없이 사전에 정한 비교로 종료했다.
